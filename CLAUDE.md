# Claude Code Session Manager

Electron desktop app — local cockpit for Claude Code CLI. Terminal + 25+ config/observability/scheduling tabs (Settings, Skills, Hooks, MCP Servers, Agent Library, Tag Library, Tasks, Plans, History, Scheduler, Web Remote, Memory, Permissions, etc.). Mobile web cockpit at bilko.run (v2: same-origin relay + session state/summary protocol).

All session-manager per-project operations live under `session-manager-operations/` at the repo root — e.g. `session-manager-operations/prompt-sessions/` (Epics), `session-manager-operations/scheduler/` (PRDs + queue), `session-manager-operations/project-brief/` (Home's Brief), `session-manager-operations/HUMAN_LEARN/`. Each is governed by the single-writer law (see below).

## Domain model (TAB / EPIC) — foundational, keep every surface consistent with this

The vocabulary for what grounds an Epic's session is **Agent** (an Agent Library persona — the
"who") **+ Tag** (the Epic's mission — the "what"), surfaced identically in the New Epic card,
Agent Library, and Tag Library — this is a current-terminology/UI update, not an API rename:
`PromptSession`'s `agentType`/`tag` fields, the `EpicTag` union, and "Epic" as the unit-of-work
noun are unchanged. Don't describe either library as read-only in new docs/copy — see their own
bullet below.

- **TAB = file location = Main Project.** A Terminal tab is anchored to one cwd; that cwd IS the project identity. Everything the app manages for a project keys off this path.
- **`<TAB cwd>/session-manager-operations/`** — the per-project operations root, created when a tab first opens on that cwd. Definitive path; session-manager owns and manages its contents (`scheduler/epics/<epic-id>/prds/`, `scheduler/state/`, `prompt-sessions/`, `HUMAN_LEARN/`, …).
- **EPIC = one small unit of work within the Main Project.** Implemented as `PromptSession` (`state/promptSessions.ts`). Each Epic carries an initial intent tag (**feature / bug / discussion** — expected to gain more clarity/kinds over time) and its `goalText`. The tag also sets how eagerly `/develop` should fire inside that Epic's session — see the `session-manager-dev:develop` skill's "Tag-aware default": `feature`/`bug` treat PRD decomposition as the expected next step, `discussion` keeps `/develop` available but never assumed until whether-to-build is actually settled.
- **New Epic creation is two independent selections, not one.** `agentType` (who runs the session — an Agent Library persona, `~/.claude/agents/*.md`, edited in the `AgentLibrary.tsx` list+detail editor) and `tag` (the Epic's **mission** — what it's for; its 5-tag taxonomy is a closed union and stays fixed, but `TagLibrary.tsx` is no longer read-only either) are separate axes on `PromptSession`. Neither library is a plain read-only directory any more: `AgentLibrary.tsx` is a full CRUD editor (New/Duplicate/Save/Revert/Delete, plus dropping a project's local overlay) writing straight to `~/.claude/agents/<name>.md` via `agentLibrary.cjs`'s `savePersona`/`deletePersona`/`removeOverride`, and each persona now carries a `tags:` frontmatter field (`AgentPersona.tags`) recording which of `TAG_LIBRARY`'s tags it's associated with — a many-to-many membership editable from either page (`AgentLibrary.tsx`'s tag-assignment chips, or `TagLibrary.tsx`'s "agents carrying this tag" list), both writing through the same `savePersona` call so the relationship has one source of truth regardless of which side you edit it from. Both field names are chosen to match this app's existing global vocabulary rather than inventing new ones: `tag` is the same field `lib/tagLibrary.ts`'s `TAG_LIBRARY`/`lib/agentTagDefs.ts`'s `AGENT_TAG_DEFS` already describe (never a second, drifted copy of a tag's mission text — every "what does this tag mean" string reads through `agentTagDef(tag).description`), and `agentType` reuses the exact field name Claude Code's own hook payloads (`SubagentStart`/`SubagentStop`'s `agent_type`), the Task tool's own `subagent_type` parameter (tracked as `subagentType` in `state/live.ts`'s `ToolUseTrace`), and a Team member's persona field in `teams.cjs` (`agentType`) all already use for "which persona is this" — not a fourth name for the same concept. `NewEpicCard.tsx` renders them as two side-by-side columns — "1 · Agent — who is working" (a real button list from `window.api.agents.listPersonas()`, defaulting to "Default") beside "2 · Mission — how they work" (the feature/bug/discussion pills, previously mislabeled "Type") — so it's visually obvious two different pickers are being set, not one. `lib/epicIntake.ts`'s `composeEpicIntake` folds the chosen persona's name+description into `openingPrompt` (never `goalText`) as a framing line that comes before the tag's own grounding template — the "who" is read before the "what". `agentType` folds into `openingPrompt` as described above, and now also sets the launched process's `--model` default for both views of that Epic's session: the chosen persona's own `model` frontmatter field wins when set and isn't `'inherit'`, else it falls back to the existing global default. `chatRunner.cjs`'s headless Chat launch resolves this via `src/main/lib/agentModelResolve.cjs`'s `resolveEpicModel` (main-process, falls back to `sonnet`); `EpicTerminalPane.tsx`'s Terminal launch mirrors the same persona-first logic renderer-side (its own `resolveEpicModel`, falling back to the raw-session-model toggle) since it can't import a `.cjs` main module — so Terminal and Chat agree on which model that session runs with even though the fallback literal differs per view. Beyond `--model`, `agentType` stays display-only — it does not otherwise change which claude CLI process spawns. An "advanced" toggle in the card header flips it (real CSS 3D flip, `rotateY`) to a read-only **grounding board** — `lib/groundingBoard.ts`'s `computeGroundingBoard` inventories the real System (`~/.claude/`) / Project (`<cwd>/`) / Local context this Epic's session will actually load (CLAUDE.md files, skills, mcp servers, hooks, the selected persona's own file, git branch, open Terminal tabs, other Epics in the project) via `window.api.config.*` reads — never fabricated placeholder numbers. It has no toggle-what-loads controls: session-manager cannot tell the `claude` CLI to skip a file it would otherwise discover on disk, so the board is deliberately an inspector, not a control.
- **The Epic's opening prompt is built from the AIM framework — Actor, Input, Mission, in that order — and all three get an explicit line, not just two.** Actor = the chosen `agentType` persona (`You are acting as the "<name>" agent: <description>`). Input = what's grounding the session, stated via `lib/groundingBoard.ts`'s `summarizeGroundingBoard(groups)` — a pure, no-extra-IO summary of the same real System/Project/Local inventory the grounding board UI already computed (`board` state if "advanced" was opened; computed fresh via `computeGroundingBoard` at submit time otherwise, in `NewEpicCard.tsx`'s `handleCreate` — never a second fetch path). Mission = the tag's `initialPromptTemplate`, followed by the human's own goal text. `lib/epicIntake.ts`'s `composeEpicIntake` composes exactly this order (`agentName`/`agentDescription` → `inputSummary` → `tag` → `goal`) into `openingPrompt`; each of the three inputs is independently optional and simply omits its line when absent — callers that never ground an Epic against a real project (e.g. `EpicQueue.tsx`'s scripted 'build' Epic) still work, they just carry a thinner prompt. This is deliberately still just a *framing line*, same status as the Actor line it sits beside — Input stays real-data-derived and display-only, never fabricated, and never a second source of truth for what the `claude` CLI itself loads.
- **Settings (System/Project/Local scopes) is substrate, not per-Epic curation — never confuse the two.** `Settings.tsx` (and its siblings Permissions/Hooks/MCP Servers/Skills) edits on-disk `settings.json`/`.claude/` files at exactly three file-level scopes (`lib/scopes.ts`'s `SETTINGS_SCOPES`: `~/.claude/settings.json` user, `<cwd>/.claude/settings.json` project, `<cwd>/.claude/settings.local.json` local) — the same files the `claude` CLI itself reads from disk on *every* invocation it launches, identically, regardless of which Epic. It was never scoped to "one session" in the old TAB=session model either; that model just made the distinction invisible because a TAB's one session and its one project settings.json had matching lifetimes. Now that one TAB hosts many EPICs, a Settings edit at Project scope changes the substrate for **every current and future Epic in that project** (User scope: every Epic machine-wide) — Settings holds no per-Epic override for most fields, and `groundingBoard.ts` only *reports* that these files exist (`inputSummary`'s one-line mention) rather than injecting their content. The per-Epic curation layer is Agent + Tag, not Settings: `agentType` (Actor) and `tag` (Mission) are folded into `openingPrompt` fresh at that one Epic's creation via `composeEpicIntake` (see the AIM bullet above) — that's the only place "how this specific Epic should work" belongs. **`model` is the one Settings-adjacent field carved out per-Epic, not per-scope**: `agent-model-default-terminal`/`agent-model-default-chat` wired `src/main/lib/agentModelResolve.cjs` so the chosen persona's own `model` frontmatter field sets the `--model` a given Epic's session launches with (falling back to Settings' "Model & Reasoning" default only when the persona has none or is `'inherit'`) — see the AIM bullet above. Every *other* field in Settings' "Model & Reasoning" group — `effortLevel`, `fastMode`, `alwaysThinkingEnabled`, and the rest — remains substrate-only with no per-Epic override: no `--effort` flag or equivalent exists in this codebase's `claude` CLI invocations today, so those stay a known gap for a future PRD once a real CLI mechanism is confirmed, not something the Agent persona can already carry. **Rule: if a behavior should differ per Epic or per task, it is a new/edited Tag (`TagLibrary.tsx`'s `initialPromptTemplate`), a new/edited Agent persona (`AgentLibrary.tsx`'s persona file, including its `model` field), or, for reasoning/effort settings specifically, a future PRD — never a plain Settings edit.** Settings otherwise holds what's legitimately identical for that scope regardless of task: permissions, hooks, MCP servers, env vars, output style, and (pending that future PRD) default effort/reasoning mode. If a user wants "this kind of task to run with a different settings.json," the correct lever today is authoring a custom Tag or a custom Agent (model included), not touching Settings. Per `agent-model-nav-consolidation`, Settings' curated "Model & Reasoning" card is demoted to advanced/raw-JSON-only (out of the default Guided/Tree view) since its one per-Epic-wired field, `model`, is now edited from Agent Library's persona detail editor instead — `effortLevel`/`fastMode`/`fastModePerSessionOptIn`/`alwaysThinkingEnabled`/`availableModels`/`modelOverrides` are still Settings-only, just reachable via "show advanced" now rather than the default view.
- **An Epic's title + objective are fixed for the life of its session, and are its first prompt.** The New Epic card composes both through `lib/epicIntake.ts` and sends the objective into the Epic's session at creation — the Epic opens with the agent already working, and nothing rewrites `goalText` afterwards (iteration happens in follow-up messages). One short-lived Epic per unit of work is the intended shape; don't mutate an Epic's goal to repurpose it, start a new one. The queue row menu's rename action (`renameEpic` in `state/promptSessions.ts`) is a narrow carve-out to this: a cosmetic title/goal-text correction (typo, clarity), never a re-purposing of what the Epic is for.
- **An Epic's lifecycle is its single `status` field, specified in [`prompt-sessions/README.md`](session-manager-operations/prompt-sessions/README.md#lifecycle).** That section is the functional requirement. Exactly three states — `proposed` (not started: an agent asking, OR a human still composing), `active` (session running, authoring PRDs, receiving scheduler updates), `completed` (archived). There is no `draft` state; a half-typed Epic is `proposed`. **Every Epic is born `proposed`; nothing is created directly as `active`.** One transition `proposed → active`, reached either by **Approve & start** or by submitting the first prompt in the New Epic flow — that submit IS the transition, not a second kind of creation. A `proposed` Epic is a valid minimal row (`id` + `claudeSessionId` are enough — reserved and ready to spawn; goalText/openingPrompt fill in later) and is **never erased**; only `markCompleted` removes it, by archiving it, or `deleteEpic` (queue row menu, `state/promptSessions.ts`) hard-removes it with no archive — guarded to refuse a live scheduler job/chat run/attached Terminal session. Only the persisted `status` may be shown as the Epic's state — run activity is **session** state, not Epic state. Three entities own their own properties: **EPIC** controls the session, **SESSION** writes the PRDs, **PRD** carries its own. New tracking/display fields go on the entity whose lifecycle they share. Don't restate any of this elsewhere; link there.
- **An Epic is created in exactly ONE place: the human pressing New Epic.** This is the SINGLE-CREATOR LAW, enforced fail-closed in `src/main/lib/epicMint.cjs` — `ensureEpic()` is join-only for every caller except `lib/promptSessionsCreateEpic.cjs` (the New Epic card's IPC handler), which is the sole holder of `MINT_AUTHORITY_NEW_EPIC_UI`; anyone else asking for an Epic that doesn't exist gets a throw plus an `epic_mint_refused` audit event. There is no agent-facing proposal channel: `/propose-epic`, `scripts/propose-epic.cjs`, the RCA hook's auto-filed Epics and the watchdog's feedback sweep are all **removed (2026-08-02)**, as `/process-feedback` + `/my-feedback` and `session-manager-operations/feedback/` were before them (historical contents archived to `feedback/archived-2026-08-02/`). An agent that is sure work is needed runs **`/develop`** inside the Epic it is already in — PRDs join an existing Epic, they never conjure one. An agent that is not sure says so and lets the human open an Epic. `status: 'proposed'` remains the birth state of every Epic and the gate before anything runs: nothing is spent until someone presses **Approve & start** (`EpicApprovalBar`), which sends its `openingPrompt` (falling back to `goalText`) as the session's first message.
- **A scheduler job's question comes back to the session that wrote the PRD.** A job parked in `needs_review` is a question, not a result. `lib/rcaReport.cjs` writes a deterministic root-cause report next to the run's own log (`runs/<runId>/root-cause-<slug>.md`, mirroring the DoD gate) and `scheduler.cjs`'s `notifyNeedsReview` appends it as a `response` event on the AUTHORING Epic's chain, resolved from the PRD's `sourcePromptId` (falling back to the job's `epicId`) — the same channel `notifyOriginatingTab` uses for completed/failed. Join-only: if no open authoring Epic exists, the report + the Scheduler tab are the whole record. This is also why PRDs must be written to the point: the clearer the PRD, the less there is to route back.
- **EPIC : claude-session = 1:1 — an Epic IS a tagged claude session.** Each Epic mints its own `claudeSessionId` (never shared with or derived from any SessionTab's sessionId), and the Epics list is the user's list of tagged sessions they iterate in. **Chat and Terminal are two VIEWS over that one session, never two sessions**: Chat = headless `claude -p --resume <claudeSessionId>` via chatRunner; Terminal = interactive PTY `claude --resume <claudeSessionId>` in the Epic's cwd. Switching views must hand off the session (mutually exclusive attachment), not mint a new sessionId — context continuity across the switch is the invariant. The Epic is the context root for that session; `EpicDetail.tsx`/`EpicComposer.tsx` render the claude session *in the Epic's context* on screen. Its event chain (`prompt → prd_created → response → closed`, FK-linked via `causedByEventId`) is the auditable trace of everything the Epic spawned, including PRD-dispatch chips.
- Persistence: active Epics in `session-manager-operations/prompt-sessions/active-index.json`; completed ones archived one JSON per Epic in the same folder (`promptSessionArchivePath`). An archived Epic's claudeSessionId is dead — resuming mints a new session with `resumedFromId` tracing back.

- **Scheduler = a browser over TAB → EPIC → PRD** (implemented 2026-07-31, v0.39.4). The Scheduler tab is a viewer/operator surface on this hierarchy — scoped to the active TAB's project by default ("All projects" is the explicit machine-wide escape hatch). On disk, per project: PRD sources in `scheduler/epics/<epic-id>/prds/` (every new PRD auto-mints/joins an Epic via `lib/epicMint.cjs` — flat `scheduler/prds/` is RETIRED and auto-consolidated into `prds-archived/` at boot), queue + history shards in `scheduler/state/` (`lib/queueStore.cjs`). Global bookkeeping is retired; what remains machine-level is Session-Manager runtime only: `~/.claude/session-manager/scheduler-machine.json` (policy/pause), run logs under `scheduled-plans/runs/`, and the **session slot pool** (`lib/sessionSlots.cjs`) — one machine-wide pool of ≤3 concurrent `claude -p` sessions that scheduler jobs AND chat runs must acquire from. Surfaced in the "Session-Manager" Configure nav tab + the Home "Active sessions" widget.
- **One TAB per project.** The sidebar button is "Open / Start Project" (native folder picker; New Folder = start). Picking an already-open project activates its existing tab — extra sessions within a project are Epics, not tabs.

- **Single-writer law over the operations root** (`src/main/lib/opsOwnership.cjs`). Every `session-manager-operations/<namespace>/` folder has exactly ONE owning surface that may write it; everyone else reads freely. Owners today: `prompt-sessions → epics`, `scheduler → scheduler`, `project-brief → project-home`, `browser → browser`, `bilko-host → bilko-host`. It is **fail-closed** — a write by an undeclared writer, or into a namespace with no declared owner, throws. Every write path enforces it (`config.cjs`'s `writeTextAtomic`/`writeBinaryAtomic`/`writeJson`/`writeJsonSync` via `opts.writer`, plus `lib/epicMint.cjs` and `lib/queueStore.cjs`, which use raw `fs`). Renderer callers declare theirs through the IPC payload (`config.writeJson(path, data, 'epics')`). Cross-writer exceptions are narrow, path-scoped **delegations** declared in one table — today only the scheduler writing `prompt-sessions/active-index.json`. Adding a namespace or writer is a deliberate edit to that file, not an implicit consequence of calling `fs.writeFile`. Each `OWNERS` namespace has its own `README.md` at its folder root (`prompt-sessions/README.md`, `scheduler/README.md`, `project-brief/README.md`, `bilko-host/README.md`) documenting its on-disk shape, sole writer, and lifecycle — read the namespace's README before writing code that touches it; `browser` has no README yet (no PRD has needed to document it).
- **No "general" OWNERS namespace exists, and none is needed right now (decided 2026-07-31).** `architecture/`, `design-mocks/`, `HUMAN_LEARN/`, `reviews/`, `logs/`, `project-pages/`, `feedback/` (retired, see above), and `bilko-host/` also live under `session-manager-operations/` but are deliberately NOT in `OWNERS` — they are written directly by Claude Code skills (e.g. `explain-to-me` writes `HUMAN_LEARN/`) via the `Write` tool, outside the app's own IPC-mediated write path, which is why `assertOpsWrite`'s fail-closed check doesn't (and isn't meant to) block them: that check only guards `config.cjs`'s own write helpers and the two raw-`fs` modules (`epicMint.cjs`, `queueStore.cjs`), not arbitrary filesystem writes by tooling. This is the correct split, not a gap: `OWNERS` governs *app-owned runtime state* (Epics, PRDs/queue, the Brief) where two writers racing would corrupt a JSON source of truth the app reads back every session; the skill-authored folders are *documentation/artifact* output with a single human-or-agent author per invocation and no concurrent-write hazard to guard against. Revisit only if a genuine cross-cutting, non-tab-specific *runtime* write need appears with no existing namespace to hold it — don't add a speculative `general` namespace ahead of that. **`browser/` is the one exception that IS in `OWNERS`** (narrow write grant in `config.cjs` for Capture-panel scratch saves) despite looking like an artifact folder — don't move it out without checking `opsOwnership.cjs` first. Any new top-level folder under `session-manager-operations/` must land in this enumeration or in `OWNERS` in the same PR that creates it — see `session-manager-operations/architecture/ops-maintenance-protocol.md` for the drift this causes when skipped (its Pattern A found this exact enumeration out of date and `feedback/`'s retirement status contradicted between two bullets in this very file — both now resolved).

Any new feature touching sessions, navigation, or per-project state must map onto this TAB→operations-root→EPIC→session hierarchy rather than inventing a parallel scoping scheme.

## Stack

Electron 33 (CommonJS main + preload) · React 18 + Vite · Tailwind · zustand · xterm + node-pty · Whisper (ricky0123/vad-web + onnxruntime-web) for voice.

## Commands

- `npm run dev` — Vite + Electron with HMR. `SM_DEV=1` is set automatically.
- `npm run build` — production renderer build into `dist/`.
- `npm run typecheck` — `tsc --noEmit`. Must pass before commits.
- `npm run test:unit` — `vitest run`. Unit tests for renderer lib/components. Single file: `timeout 120 npx vitest run <path>`. This repo does not use `node --test` — it can't resolve the TypeScript renderer imports.
- `npm run test:e2e` — Playwright Electron tests under `xvfb-run` (Linux).
- `npm run health` — `src/main/health.cjs`. Validates build (types, dist artifact, e2e infra present) + runtime (config dir writable, scheduler queue.json + PRD count, transcripts dir, stranded legacy-dir PRD migration). Exit 0 = GREEN, 1 = RED. Entry point for `/local-project-health`.
- `npm publish` — runs `vite build` via `prepublishOnly`. Tag is `latest`.

## Architecture (load-bearing files)

**Main process** (`src/main/*.cjs`):
- `index.cjs` — BrowserWindow + IPC registration. Navigation locked: `setWindowOpenHandler` denies, `will-navigate` allows only the dev URL.
- `config.cjs` — fs layer. **All paths go through `validatePath` (allowedRoots = home dir)**. Atomic writes via tmp + rename. Chokidar watchers refcounted per absolute path.
- `transcripts.cjs` — tails `~/.claude/projects/<encoded-cwd>/<sessionUuid>.jsonl`, classifies events, ring-buffers per tab, broadcasts `transcript:event:<tabId>`.
- `memoryAggregate.cjs` — Memory Clusters backend (replaced the old Knowledge Graph tab/`kg.cjs`). Reads one project's workspace memories (the `.md` files under `~/.claude/projects/<encodedCwd>/memory/`, the same store `memoryTool.cjs` owns) and, via a single cost-gated `claude -p` pass (only fires on explicit `refresh: true`), organizes them into named semantic clusters with `[[wikilink]]`-derived connections. Cache: `~/.claude/session-manager/memory-clusters/<workspace>.json`. Spawn pattern mirrors the old kg.cjs: stdin closed, model pinned, hard timeout, `SM_KG_INTERNAL=1` so the prompt-logging hook skips it, brace-matching JSON extractor.
- `chatRunner.cjs` — runs a dormant Terminal tab's chat command as a headless `claude -p --output-format stream-json` job that exits when done (first command `--session-id`, later `--resume`). Serialized through a FIFO queue at concurrency 1 (`SM_CHAT_CONCURRENCY`, clamp [1,3]) so bursts can't fan out into a parallel-`claude -p` OOM. Stop-signal protocol `<<<SM_NEEDS_INPUT>>>`+JSON lets a run ask questions.
- `scheduler.cjs` — runs PRDs from each active project's own `<cwd>/session-manager-operations/scheduler/epics/<epic-id>/prds/` (resolved via `lib/prdLocations.cjs`; queue + history shards live per-project in `<cwd>/session-manager-operations/scheduler/state/` via `lib/queueStore.cjs` — only run logs and PRD_AUTHORING.md remain under `~/.claude/session-manager/scheduled-plans/`) as `claude -p` jobs. Modes: `manual` / `on-reset` / `when-available` (default; polls billing usage every 60 s — `POLL_INTERVAL_MS` in `lib/schedulerConfig.cjs`). Auto-pause on rate-limit, auto-resume at next 5h reset. **Boot reconciliation**: on startup, reaps orphaned jobs (PIDs no longer alive) and logs outcome (success/timeout/error); a still-alive orphaned pid is SIGTERM'd and its classification deferred (`partitionBootOrphans`/`applyOrphanOutcome`, `BOOT_ORPHAN_KILL_GRACE_MS`) so its log isn't misread mid-write. **Dead-process reaper**: background process check + PID-alive validation, run-outcome classifier to detect hangs. (The heartbeat's old 5-minute feedback sweep — scanning each active project's `session-manager-operations/feedback/` and auto-queuing a `/process-feedback` PRD — is gone along with that folder and skill. A job parked in `needs_review` now writes `lib/rcaReport.cjs`'s root-cause report into its run dir and surfaces it on the authoring Epic via `notifyNeedsReview`; it never creates work on its own.) Both reduce manual cleanup of stuck PRD jobs.
- `supervisor.cjs` — every 15 min, Opus probe per running job; SIGTERMs descendant bash on stuck poll-loops without killing the agent. Cost-gated by SM_SUPERVISOR_DISABLE.
- **Definition-of-done gate** (`lib/dodDrainHook.cjs`): fires at queue-drain (when `pickNextBatch` returns an empty batch). Re-verifies each completed PRD's AC live (`reverifyBatch`), flags risky surfaces (`flagRiskySurfaces`), writes `runs/<ts>/definition-of-done-<key>.md` (`writeReport`). Idempotent: `batchKey` (excludes dod/meta slugs) + `reportExists` make a re-drain over the same completed set a single fs-stat no-op. Non-blocking: called fire-and-forget from `tickQueue`; errors are logged not thrown. Skipped when `state.paused` (covers rate-limit), `cancelToken.cancelled`, or no completed jobs. Kill-switch: `SM_DOD_DISABLE=1`.
- `scripts/scheduler-watchdog.cjs` + `scripts/scheduler-watchdog.sh` — external check-and-exit watchdog running outside Electron via systemd user timer or cron (every 2–3 min). Its only job (post PRD 685/686): heartbeat-gated liveness check → `maybeRelaunchApp()` if stale-and-dead. Queue-orphan reconciliation lives in `scheduler.cjs` itself (see above); the feedback sweep it used to also host is retired entirely — do not reintroduce either here. Install via `scripts/install-scheduler-watchdog.sh` (idempotent; `SM_WATCHDOG_DRYRUN=1` for preview).
- `pty.cjs` — node-pty per tab, keyed by renderer-generated UUID = claudeSessionId.
- `ipcSchemas.cjs` — zod schemas validate IPC payloads at the main-process boundary.
- `teams.cjs` — enumerates `~/.claude/teams/<name>/config.json`; gates the `TeamsCard` team chip behind `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS`.
- `queueOps.cjs` — scheduler PRD queue linter (unbounded-loop + post-AC overrun detection) + archive + retag.
- `pluginInstall.cjs` — hidden-pty plugin install via `claude plugin install <slug>`. Slug regex `/^[a-z0-9\-/]+$/`, 5 min kill ceiling, single in-flight per slug.
- `memoryTool.cjs` — workspace-scoped memories CRUD for the `memory_20250818` tool.
- `webRemote.cjs` — same-origin relay server for web-remote mobile cockpit. Ping/auth/session state/summary RPC endpoints. Rate limits + audit log.
- `adminServer.cjs` — loopback-only, token-authed HTTP admin API (127.0.0.1, OS-assigned port, token in `~/.claude/session-manager/admin-api.json`). Narrow surface: list scheduler jobs + reset one stuck job. Wrapped as MCP tools by `scripts/scheduler-mcp-server.cjs` (registered in this repo's `.mcp.json`) — `scheduler_reset_job`/`scheduler_list_jobs` only work while the Electron app is running, since that's what hosts the admin server.

**Renderer** (`src/renderer/`):
- `state/config.ts` — per-path FileState with dirty tracking. Backed by config.cjs IPC.
- `state/live.ts` — per-tab derived state (todos, plans, agents, usage) fed by transcript events. Subscribed to `transcript:event:<tabId>` from main process.
- `state/voice.ts` — voice store + auto-submit timer + idle-stop timer + drain watchdog.

Three per-level affordance helpers keep the rules in the lib rather than scattered in JSX: `showsToolStrip` (a *completed* assistant turn's own strip + its diff cards, same 1–2 rule), `showsInjectedPreamble` (level 1 only — see `promptPreamble.ts`), and `ASSISTANT_CLAMP_CHARS` (level 5 only, behind a per-turn "Show full message"). **Two invariants outrank the dial:** a turn asking the human something is never hidden or clamped at any level (hiding a `question`/`notice` strands a run waiting on an answer nobody can see), and the **in-flight** bubble keeps its tool strip at every level (mid-run it's the only progress signal there is). Nothing is dropped from the store, so raising the level restores the byte-exact record with no re-read. Prefs persist to `~/.claude/session-manager/chat-prefs.json` as a global default + sparse per-Epic override, with a one-line forward-migration of the retired 3-level `verbose` value. This is a filter on *reporting*, distinct from `ChatTranscriptTurn.tsx`'s event router, which remains "a router, never a filter".
- `lib/promptPreamble.ts` — the FIRST feature gated on that dial. `chatRunner.cjs` prepends `STOP_SIGNAL_INSTRUCTION + CHAT_MODE_TRUTH_INSTRUCTION` (~1.4k chars) to every prompt, and since the CLI's JSONL records what it was actually sent, the transcript-derived user turn is mostly boilerplate with the human's sentence at the bottom. `splitInjectedPreamble(text)` peels those blocks off for display, and `Turn`'s `injectedPreamble='hidden'` collapses them behind a tiny `≡` glyph (EpicDetail passes `'hidden'` at every level but 1, via `showsInjectedPreamble`). The renderer can't import the main-process `.cjs`, so each block is anchored on its **first and last sentence only** rather than a copied literal — `src/main/__tests__/chat-preamble-anchors.test.cjs` composes the REAL exported constants and fails if a rewording breaks the anchors. The splitter refuses to strip when a block's closing sentence is missing, when stripping would empty the bubble, or when the boilerplate appears anywhere but the very front (a human quoting it). `turn.text` is never rewritten — the raw footer still yields the byte-exact sent prompt; only Quote narrows to the human's own words.
- `lib/prettyModel.ts` — single source of truth for model-name shortening (incl. `[1m]` context-suffix); every pill/chip that shows a model name imports it — don't reintroduce a local copy.

## Renderer data flow

The renderer uses isolated zustand stores (no cross-store subscription). Data flows: **main process → IPC broadcast → store subscription → selector → component hook**.

1. **Main process** publishes events (config changes, transcript events, schedule updates, etc.) as IPC broadcasts: `config:changed`, `transcript:event:<tabId>`, `schedule:snapshot-changed`, etc.
2. **Zustand stores** subscribe to IPC broadcasts and update their state. Each store is independent; components cannot trigger store-to-store updates.
3. **Components** consume stores via hooks (`useConfig()`, `useLiveTab()`, `useScheduleState()`, etc.). For multi-store queries, compose selectors in the component or use memoized helpers.
4. **Panes** (SchedulePanel, History views) own local UI state (filters, collapsed sections) separate from global stores. Panes are stateless containers that accept props for the data they display.

## Conventions

- **Tab ID = claudeSessionId** by design. Used for `--session-id` pass-through and JSONL transcript file lookup.
- **No CommonJS in renderer**, no ES modules in main — `type: module` is set but `.cjs` files for main/preload bypass it.
- **Settings.json validation**: monaco `jsonDefaults` + schemastore.org. No hand-rolled zod for user config.
- **Hot data contiguous**: live state per tab is a flat object, not nested per-event.
- **No backwards-compat shims**: this is a single-author project; just rename and refactor.
- **Privacy invariant**: `RecordingStatus` (App-level, top of window) MUST be mounted whenever `isRecording === true`.
- **Toast is the user-facing error channel** — don't swallow errors silently; surface via `useToast().show('error', msg)` (or `toast.error(msg)`) so the user sees the failure. Background hydrate paths can stay logger-only.

## Conventions (extensions for v0.20+)

- **Almanac design** (Scheduler): SchBadge status colors + project-dot palette. Single source of truth in `sched-primitives.tsx`.
- **Renderer state stores** (zustand): separate concerns: `config.ts` (file-backed, dirty-tracked), `live.ts` (per-tab derived from transcripts), `voice.ts` (voice UI), `scheduleState.ts` (queue + history), `toast.ts` (toast messages). ## Avoid

- Launching a `claude -p` process **without acquiring a slot from `lib/sessionSlots.cjs`** first. That pool (default 5, user-adjustable [0,10] from the Home tab, `SM_SESSION_SLOTS` overrides) is the single machine-wide concurrency limit — scheduler jobs *and* chat runs draw from it. The scheduler's own `concurrencyCap` is **retired**: it was the exact per-consumer private cap sessionSlots.cjs was written to replace, and it silently ceilinged the queue at 3 while the Home tab reported 5. Do not reintroduce a private cap in any consumer. OOM protection is the *memory gate* in `tickQueue` (`RESERVED_HOST_MB` 3000 + `MIN_FREE_MB_PER_JOB` 2500), which is machine-aware — not a hardcoded job count; the 2026-06-10 five-parallel OOM is covered there.
- Gating scheduler batches on **`parallelGroup`**. It is a unique-per-PRD number (PRD 832) and a display/priority hint only — never a barrier. `dependsOn` is the sole ordering primitive. `schedulerBatch.cjs` used to fire one `parallelGroup` per tick and hold every higher one; with unique numbers that reduced every batch to exactly **one job** (measured max concurrency 1 across 25 runs against a 5-slot pool), and because numbers are allocated monotonically upward, each newly queued PRD was always held behind the in-flight one. Removed 2026-08-02; regression coverage in `schedulerBatchDepends.test.cjs`.
- Adding `shell: true` to `child_process.spawn` calls — only `watchers.cjs` and `app:test-fire-hook` legitimately need it (user-supplied shell strings are part of those features). Anywhere else, pass argv arrays.
- Reading remote URLs in production — `createWindow` hard-fails if `dist/index.html` is missing rather than falling back to `localhost:5173`.
- Re-implementing the tmp+rename atomic-write pattern. Use `config.cjs`'s `writeJson` / `writeTextAtomic`.
- Cross-subscribing between renderer state stores — e.g., don't read `live.ts` from `config.ts` or vice versa. Each store is an island; components compose them via hooks. Complex queries go in components or memoized selectors, not in store initialization.
- Adding pane-specific state to parent tabs — if a SchedulePanel needs filter persistence, keep it in the pane, not the tab. Panes own their UI concerns; tabs own layout + navigation.
- Importing design primitives via wildcard (`import * as SchElements from ...`) — requires explicit named imports to prevent accidental cross-system usage.
- Returning a freshly-built value from a zustand selector — `useStore((s) => s.x ?? [])`, `?? {}`, `.filter(...)`, `.map(...)`, `Object.values(...)` inside the selector. zustand v5 compares snapshots by reference via `useSyncExternalStore`; a new reference per call means infinite re-render → React #185 → **the whole app renders blank**. Select the raw slice (fallback via a module-level stable constant like `EMPTY_JOBS`) and derive after. Three incidents now: TabBar (see its header comment), an earlier e2e blank-app, and the v0.39.0 boot blank-screen (TerminalChat `scheduleJobs`, fixed in `4ab267b`). Guarded by `npm run lint:selectors` (`scripts/check-unstable-selectors.cjs`) — a fast grep-based check for this exact pattern; run it alongside typecheck.
- Adding a new LeftNav tab for a live/observability feature before checking whether an existing surface (Terminal, Scheduler) already owns that data. Treat each nav destination as an independent "micro-service" — before adding one, check if an existing item already owns the data/job and extend it (a sub-tab) instead of shipping a parallel UI. When two surfaces read the same underlying state, consolidate rather than duplicate. The nav has been pruned once already (2026-06-03: Scheduler/Plans/Background-Agents merged into one Scheduler destination) after growing to ~31 destinations with real overlap.
