Three walkthroughs

Human → code

  1. You type build me X. develop clarifies any genuine ambiguity, explores the repo.
  2. It decomposes X into small PRDs (sizing per prd), appends standards.md, writes them to the queue.
  3. It confirms each PRD (filename, group, cwd, ETA), then enters Phase 2.
  4. Every ~30 min it checks the scheduler; if a PRD stalls or trips needs_review, it surfaces that to you.
  5. On success it verifies live against the AC, optionally runs requesting-code-review, and reports what landed.

Agent feedback → code

  1. Another project drops a file in feedback/. process-feedback reads it, verifies the claims against real code.
  2. It classifies: ours-do-it → develop; ours-decline → documented decline; theirs → my-feedback upstream.
  3. For the "do" items it hands develop a complete brief (goal + the feedback's own AC + cwd + reuse notes); the item is marked 🛠 queued, not ✅, and archived immediately.
  4. develop Phase 2 tracks + verifies (same as the human path) and reports.
  5. project-status's next audit reconciles the 🛠 row to ✅ once the queued PRD lands.

Cron → KPI lever → code

  1. A daily firing runs optimize-kpi: measure the North-Star KPI, grade the lever filed last time, audit usage + operational logs.
  2. 3 independent recommenders diagnose the gap in parallel; a consolidator picks the single highest-leverage lever, rejecting anything not grounded in the usage/log evidence or already in flight.
  3. It writes one feedback item into this project's own intake and invokes process-feedback, scoped to that file.
  4. From here it's the agent-feedback walkthrough above: process-feedback → develop (or my-feedback if the winning lever is actually upstream-owned).
  5. project-status's next run only re-triggers optimize-kpi once health is fully green — a degraded base gets routed to develop/my-feedback first.
