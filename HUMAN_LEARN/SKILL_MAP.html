⛓ Skill Map — the local-development chain

How a request becomes shipped code on this machine. Two entry points feed one pipeline: an interactive human prompt, and an agent feedback file dropped in by another project. They differ only in intake shape — everything from /develop onward is identical. Each skill lives at ~/.claude/skills/<name>/SKILL.md (or ~/.claude/commands/), carries an explicit Role and Never, and references — never forks — the others.

The principle: intake may differ, the pipeline is identical. A human line and an agent feedback file are two doors into the same room. Only triage + bookkeeping differ (interactive clarification vs feedback file + README log); decompose → queue → track → verify → report is one implementation with two callers.

Two walkthroughs

Human → CODE

  1. You type build me X. /develop clarifies any genuine ambiguity, explores the repo.
  2. It decomposes X into small PRDs (sizing per /prd), appends standards.md, writes them to the queue.
  3. It confirms each PRD (filename, group, cwd, ETA), then enters Phase 2.
  4. Every ~30 min it checks the scheduler; if a PRD stalls or trips needs_review, it surfaces that to you.
  5. On success it verifies live against the AC, optionally runs requesting-code-review, and reports what landed.

Agent → CODE

  1. Another project drops a file in feedback/. /process-feedback reads it, verifies the claims against real code.
  2. It classifies: ours-do-it → /develop; ours-decline → documented decline; theirs → /my-feedback upstream.
  3. For the “do” items it hands /develop a complete brief (goal + the feedback’s own AC + cwd + reuse notes); the item is marked 🛠 queued, not ✅.
  4. /develop Phase 2 tracks + verifies (same as above) and reports — /process-feedback consumes the outcome.
  5. Once landed + verified, the feedback flips 🛠 → ✅, gets a final RESOLUTION, and is git mv’d to processed/; the intake README folds in the lesson.
