Terminal & Live State — one UUID ties everything together

pty.cjs · transcripts.cjs · state/live.ts · App.tsx

The core trick of the whole app: the tab ID is the Claude session ID. The renderer mints a UUID, launches claude --session-id <uuid> in a pty, and because Claude Code names its transcript file after that same UUID, the app knows exactly which JSONL file to tail for that tab — no guessing, no scanning. Everything live (todos, plans, subagents, usage) derives from that tail.

1 · Tab creation renderer

Creating a tab mints crypto.randomUUID() (App.tsx:244) and renders the launch command from the active preset: claude [--dangerously-skip-permissions] --session-id <uuid> (lib/presets.ts:53-55, also lib/createPickedSession.ts:19). The UUID is the tab key in every store and every IPC channel from here on (state/sessions.ts:7).

2 · PTY layer electron main

pty.cjs spawns a node-pty interactive shell (xterm-256color) per tab keyed by that UUID and writes the startup command into it — so the terminal survives Claude exiting and behaves like a real shell. Data/resize/exit flow over per-tab IPC channels; output is chunked at 60 KiB so a huge paste can't stall the IPC pipe. Closing a tab kills the pty and tears down its channels.

3 · Transcript tailing electron main disk

transcripts.cjs resolves ~/.claude/projects/<encodeCwd(cwd)>/<uuid>.jsonl — the same encodeCwd slug convention the Knowledge Graph uses (transcripts.cjs:11) — and tails it with a chokidar watcher (awaitWriteFinish: 30 ms stability / 20 ms poll, transcripts.cjs:321). Each JSONL line is classified into one of 8 event types (assistant text, tool use, todos, plan, subagent activity, usage, …), oversized raw strings truncated at 4,096 chars (transcripts.cjs:46), buffered in a 500-entry ring per subscription (transcripts.cjs:181-183), and broadcast on transcript:event:<tabId>. Subscriptions are capped at 20 concurrent (transcripts.cjs:228) and ref-counted, so two consumers of one tab share a single watcher.

4 · Live state renderer

state/live.ts subscribes per tab and reduces the event stream into one flat object — todos, current plan, subagent rows, token usage, and a 32-slot activity ring — "hot data contiguous" by convention: no nesting per event, just the latest derived truth. Sub-collections are bounded (50 agents/plans/tools) and replay on mount is suppressed so re-opening a tab doesn't re-animate history. Consumers: the terminal tab's overlay panes and the status bar (the old AgentView tab was deleted 2026-06; its monitor rows folded into the Subagents Live view).

5 · Lifecycle

  • Close — pty killed, watcher ref-dropped, live-state slot discarded.
  • Restart — a new UUID (new transcript identity), unless…
  • Resume — when the old transcript exists on disk, the tab relaunches with claude --resume <id> so transcript + plan continuity survive (App.tsx:235).

Scheduler — PRDs become autonomous claude -p jobs

scheduler.cjs (~2,000 ln) · supervisor.cjs · queueOps.cjs · lib/schedulerConfig.cjs

Drop a PRD markdown file into a folder; the scheduler waits for a cheap moment on your 5-hour billing window, runs it headlessly with four overlapping watchdogs, verifies the result, and can even write its own fix-plan when a job fails. The hard-won design driver: headless jobs hang in creative ways (the fizzpop poll-hang, the etch-engine post-AC overrun) — so almost everything here is a safety net. This is the engine the dev-skill chain queues work onto.

1 · Input: the PRD queue disk

~/.claude/session-manager/scheduled-plans/
├── prds/                        # NN-slug.md — NN prefix = parallel group
├── queue.json                   # config + jobs[] + paused state (SoR)
├── runs/<ISO>/<slug>.log        # captured stdout/stderr per run
├── runs/<ISO>/<slug>.meta.json  # exitCode, duration, outcome classification
└── prds-archived/<ISO>/         # archived, never deleted

Frontmatter carries title, cwd, parallelGroup, estimateMinutes (queueOps.cjs:85-150). A reconcile pass (scheduler.cjs:486-534) walks prds/, queues new files as pending, prunes orphans. The linter blocks known footguns before they queue (queueOps.cjs:51-83): unbounded until/while true loops (error — the fizzpop incident), sequences ≥500 (error — the etch-engine incident), --no-verify/--no-gpg-sign (warn), missing cwd on disk (error).

2 · Fire policies — when does a job start? electron main

  • when-available (default) — polls the billing usage API every 10 min (POLL_INTERVAL_MS, schedulerConfig.cjs:7); fires when 5-hour utilization is below utilizationThreshold = 90%. A 429 from the meter itself fires anyway at util=0; an auth error pauses for manual resume; 30 min of network failures auto-pauses with exponential backoff capped at 8 min (scheduler.cjs:1581-1586).
  • on-reset — one setTimeout for nextReset + offsetMinutes (15 min default), reset time read from the usage API's five_hour.resets_at (scheduler.cjs:542-548, 628-637).
  • manual — only the "Run now" button.

Jobs sharing an NN- prefix form a parallel group: the group fires together (capped at concurrencyCap = 3) and the next group waits. Each slot also passes a memory gate — 1,500 MB free RAM required per job (scheduler.cjs:188) — because 5 parallel claude -p processes OOM-killed Electron on 2026-06-10.

3 · Execution — one job, four watchdogs subprocess

claude -p "<PRD body + FINISH_PROTOCOL>" --model sonnet
       --dangerously-skip-permissions --output-format stream-json
       --verbose --session-id <UUID>          # spawned detached → whole-tree kill
  • result-tail — polls the run log every 5 s for result=success; once seen, grants a 90 s grace, then SIGTERM → SIGKILL after 30 s more (scheduler.cjs:80-82). This is the anti-"post-AC overrun" net: a job that declared success cannot keep running fixture generators for hours.
  • idle-tail — SIGTERM when the log mtime stalls > 20 min (scheduler.cjs:91). Anti-poll-hang.
  • deadman — unconditional SIGKILL at 4 h (MAX_JOB_DURATION_MS, schedulerConfig.cjs:17).
  • supervisor probe (supervisor.cjs, every 15 min, Linux-only, gated by SM_SUPERVISOR_DISABLE) — when a job's log is >10 min stale, an Opus probe reads the pstree, child bash cmdlines, and log tail, then chooses kill-bash (SIGTERM the stuck descendant shell, keep the agent) or kill-agent (the job itself is wedged). All probes ring-logged (50 entries).

4 · After exit — verify, guard, self-heal electron main

  • Commit-guard (scheduler.cjs:1197-1281) — git status is snapshotted before the run; afterwards, new uncommitted files downgrade the job to needs_review instead of silently passing. Skipped when HEAD moved (job committed its work) or concurrent writers touched the tree.
  • Rate-limit detection — pauses the whole queue, auto-resumes at nextReset + 30 s.
  • Transient-kill retry — exit 143/137 in under 45 s reads as an external kill: auto-retry up to 2× (scheduler.cjs:1359-1361).
  • Fix-plan auto-recovery (scheduler.cjs:1032-1183) — on real failure, an Opus investigation (30-min deadman) reads the failure log + original PRD and writes a <group>-fix-<base>.md PRD; when the fix job succeeds, the original is auto-promoted to completed.
  • Boot reconciliation + dead-process reaper (scheduler.cjs:1934-1979, 1475-1513) — on startup and every poll cycle, orphaned PIDs are killed and their jobs classified from the run log (success/timeout/error), so a crash never wedges the queue.

5 · Renderer renderer

state/scheduleState.ts mirrors queue + history from schedule:* IPC broadcasts; SchedulePanel.tsx (Queue / PRDs / History sub-tabs, owns its own filter state) renders inside the Scheduler tab's Almanac shell (sched-primitives.tsx: SchBadge status colors, hashed project-dot palette) and is reused by web-remote.

Scheduler Watchdog — external heartbeat outside Electron

scripts/scheduler-watchdog.cjs · scripts/scheduler-watchdog.sh · scripts/install-scheduler-watchdog.sh

The in-process scheduler (scheduler.cjs) only runs while Electron is open. The external watchdog is a separate check-and-exit process invoked every 2–3 min by a systemd user timer (or cron fallback), so the queue stays healthy even when the desktop app is closed.

What it does

  • Heartbeat-gated reconcile — reconcileQueueOffline() reads the queue's heartbeat file; if Electron's in-process scheduler is running it skips to avoid double-writes. When Electron is absent it reaps orphaned PIDs and promotes jobs from running to success/timeout/error based on the run log — same logic as the in-process boot reconciler.
  • Active-session detection — activeProjectCwds() enumerates live Claude Code terminal sessions by scanning ~/.claude/projects/ JSONL files for recent mtime activity; used by sweep() to gate feedback ingestion only when a session is open.
  • Feedback sweep + auto-PRD emitter — sweep() scans ~/.claude/session-manager/feedback/ for open items, cheap-reads them, and emits PRDs into the scheduler queue so the next available billing window picks them up automatically.

Install

Run once per machine. Idempotent — safe to re-run.

bash scripts/install-scheduler-watchdog.sh

To preview without activating a live timer:

SM_WATCHDOG_DRYRUN=1 bash scripts/install-scheduler-watchdog.sh

The installer prints the exact loginctl enable-linger "$USER" command needed to keep the timer alive after logout (for headless servers or suspended laptops).

Fallback priority

  1. systemd user timer (preferred) — ~/.config/systemd/user/scheduler-watchdog.{service,timer}; OnUnitActiveSec=2min, Persistent=true.
  2. cron (fallback when systemctl --user is unavailable) — */3 * * * * with flock -n overlap protection and grep -qF idempotency guard.

The pipeline, step by step

1
Captureshell hook~/.claude/settings.json · UserPromptSubmit

Every prompt you submit in any Claude Code session fires the log-prompts-knowledge-graph UserPromptSubmit hook — a one-liner jq append. It writes one JSON line per prompt to a single global append-only log:

{ "ts": "…", "session_id": "…", "cwd": "/home/bilko/Projects/session-manager",
  "transcript_path": "…", "prompt": "the user's literal words" }
   ──append──▶  ~/.claude/knowledge-log/prompts.jsonl
  • cwd is captured here — the directory the session was launched from. This single field is what makes the whole graph per-project (step 6).
  • The hook exits early when SM_KG_INTERNAL=1 is set, so the pipeline's own claude -p calls never log themselves (no self-ingestion loop).
2
Triggerelectron mainkg.cjs:631-648 init()

The main process watches the log directory with fs.watch. The first new prompt arms a leading-edge coalescing timer (WATCH_COALESCE_MS = 5 min, kg.cjs:59); later prompts ride along instead of resetting it — so a busy session can't starve ingest, and each run sees a full window's worth of prompts. Two other ways in: the "Process now" button in the KG tab (kg:ingest IPC) and the self re-arm in step 5 when a run leaves backlog.

3
Ingest — read only what's newelectron mainkg.cjs:348-388 ingest()

A global byte-offset watermark (ingest-state.json → lastOffset) marks how far into prompts.jsonl the pipeline has committed. Each run opens the file, seeks to the watermark, and reads at most MAX_TAIL_BYTES = 8 MB of new tail — so an 80 MB backlog never lands in memory at once; the rest is drained by 3-second re-arms. A head-of-line guard (kg.cjs:379-385) skips past any single line bigger than the whole window so one pathological line can't freeze ingest forever.

4
Filter noise & plan per-project batcheselectron mainkg.cjs:63-103 isNoise · kg.cjs:313-339 planUnits()

The new tail is split into ordered units. A line is dropped as noise if it is:

  • Internal — starts with one of the pipeline's own prompt prefixes ("You extract a knowledge graph from a developer…") — belt-and-suspenders behind the SM_KG_INTERNAL env guard.
  • Automated, role-setting — matches /^\s*you are (a|an|the)\b/i. A real dev rarely opens a prompt with "You are a…"; other agents' machine prompts always do.
  • Automated, long + strict-format — over 2,000 chars and demands machine output ("return only JSON", "respond with only", <output_format>). Length alone is never enough — devs paste long diffs and stack traces.

Surviving prompts are grouped into batches of at most BATCH = 20 that never mix projects: a change of encodeCwd(cwd) closes the current batch (kg.cjs:329-335). That invariant is what makes every extracted entity attributable to exactly one graph.

5
Extract — one claude -p per batchsubprocesskg.cjs:202-228 runClaude · kg.cjs:255-275 prompt · kg.cjs:426

Each batch is sent to a headless Claude:

claude -p "<EXTRACTION_PROMPT + up to 20 logged prompts>"
       --model haiku  --output-format text
       --append-system-prompt "<EXTRACTION_SYSTEM>"
       --dangerously-skip-permissions
env: SM_KG_INTERNAL=1      stdio: ['ignore', pipe, pipe]      timeout: 180 s
  • stdin must be closed ('ignore') — claude -p otherwise blocks waiting for piped stdin and returns empty. (Hard-won gotcha, kg.cjs:206-208.)
  • EXTRACTION_SYSTEM (kg.cjs:253) sets a deterministic-extractor role so the embedded logged prompts read as inert data — without it, "You are a…" text inside the log trips Claude's prompt-injection resistance and it refuses.
  • The prompt asks for {entities, relations} JSON with 7 entity types (project · feature · tool · tech · concept · goal · person) and pre-seeds the project's top 200 known entity keys (KNOWN_VOCAB) so the model reuses keys instead of minting near-duplicates — dedup at extraction time.
  • Output is parsed by a balanced-brace scanner (extractJson, kg.cjs:231-249) that tolerates prose and code fences around the JSON.
  • Failure semantics: a transient failure (timeout / spawn / rate-limit) stops the run without advancing the watermark — fully resumable, no double-counting. An unparseable response (model refused) quarantines just that batch — advance past it and continue, so one bad batch can't freeze the graph (kg.cjs:428-451). Hard cap: MAX_EXTRACTIONS_PER_RUN = 30 claude calls per run.
6
Persist — upsert into that project's graphdiskkg.cjs:277-304 upsert · kg.cjs:454-474 commit

Entities are canonicalized (lowercase, strip leading article, collapse whitespace — kg.cjs:176-183) and upserted: an existing node gains count += 1 and a fresher lastTs; an existing edge gains weight += 1. Everything lands in one JSON file per project:

~/.claude/knowledge-log/
├── prompts.jsonl                 # global append-only log (step 1)
├── ingest-state.json             # global byte-offset watermark
├── prompt-index.json             # per-project prompt counts (sidecar)
└── graphs/
    ├── -home-bilko-Projects-session-manager.json   ◀ THIS project's graph
    ├── -home-bilko-Projects-burrow.json
    └── …one file per encodeCwd(cwd)

Crash-safe commit order per batch: graph file first (atomic tmp+rename via config.cjs writeJson), then the prompt index, then the watermark — a crash at any point re-processes at most the batch in flight, never skips one. The graph grows live, batch by batch, with a kg:ingest-progress broadcast after each commit.

7
Serve — visualize & askrendererKnowledgeGraph.tsx · kg.cjs:623-628 IPC

The KG tab talks to main over four IPC handlers — kg:get (one project's nodes+edges+status), kg:projects (project list with pending counts), kg:ingest ("Process now"), kg:ask (Q&A) — and subscribes to kg:ingest-progress for live updates (per-batch reloads coalesced at 500 ms).

  • Graph pane: react-force-graph-2d canvas force layout. Node size = mention count, color = entity type, directional arrows on edges. Node/link objects are identity-stable across reloads so the simulation doesn't re-heat (KnowledgeGraph.tsx:128-168).
  • "Ask your history" (kg.cjs:582-621): builds a context of the project's top 40 nodes + top 60 edges + 15 keyword-matched raw prompts, then one claude -p --model sonnet call answers, citing the actual prompts it used.

Per-project scoping — verified

Yes — the graph is strictly per project, keyed by the session's launch directory. The hook records cwd at submit time (step 1); encodeCwd() (src/main/lib/encodeCwd.cjs) turns it into a slug by replacing every non-alphanumeric character with - (mirroring Claude Code's own transcript-directory convention); and that slug is the graph filename: graphs/<encodeCwd(cwd)>.json (kg.cjs:129). Batches never mix cwds (step 4), Q&A filters prompts to the selected project's encoded cwd (kg.cjs:588), and on load the filename is treated as authoritative over the file's own cwd field (kg.cjs:140).
The fine print: "project" means "launch directory". /home/bilko/Projects/session-manager → -home-bilko-Projects-session-manager.json, but a session launched from a subdirectory encodes to a different slug and feeds a different graph. There is no "walk up to the git root" logic anywhere in the pipeline. Run sessions from the project root to keep one coherent graph per project.

Why it's shaped this way

LightRAG-shaped, incremental

One global watermark + per-batch commits means a rate-limit, crash, or app quit mid-run loses at most the batch in flight. The next run retries exactly those prompts — no re-extraction, no double-counted weights.

Zero native deps

JSON files for storage, claude -p for both extraction and answers. Nothing to node-gyp, so npx claude-code-session-manager never breaks on a native rebuild.

Injection-resistant by role, not by sanitizing

Logged prompts can contain anything — including other agents' "You are a…" instructions. The EXTRACTION_SYSTEM append-system-prompt declares them inert data, and the noise filter drops the worst offenders before they're ever sent.

Self-ingestion is impossible twice over

SM_KG_INTERNAL=1 stops the hook from logging the pipeline's own calls; isInternalPrompt prefix-drops any pre-fix lines already in the log.

The desktop dials out to wss://bilko.run/projects/session-manager/relay (webRemote.cjs:41) — nothing ever connects inbound to your machine, no port forwarding, no tunnel daemon. "Same-origin" means the relay lives inside the bilko.run Fastify host, so the phone app's CSP stays connect-src 'self'. Heartbeat: ping every 30 s, 3 missed pongs = reconnect with 1 s → 60 s backoff (webRemote.cjs:51-58). Pairing: an 8-char OTP shown on the phone is typed into the desktop's WebRemote tab (WebRemote.tsx:379-452); OTP verification invalidates after 3 failures.

2 · The E2E state machine electron main

idle ──e2e:hello (browser P-256 pubkey)──▶ pending_sas ──user confirms 6-digit SAS──▶ authenticated
  │                                            │
  └── plaintext READS only                     └──key/SAS mismatch──▶ failed (reconnect to retry)
  • Key agreement (webRemote.cjs:78-113): P-256 ECDH → HKDF-SHA256 (salt = deviceId, info = sm-e2e-v1) → 32-byte AES-256-GCM session key, held in memory only, reset on disconnect.
  • SAS (webRemote.cjs:120-137): a second HKDF (info = sm-sas-v1) derives a 6-digit code shown on both screens; you visually compare and confirm on the desktop (WebRemote.tsx:235-255). This defeats a man-in-the-middle relay: a MITM'd ECDH produces different codes on each side.
  • After auth, everything rides in e2e:box frames: 12-byte nonce + AES-GCM ciphertext + 16-byte tag (webRemote.cjs:143-173). Max message 256 KiB.

3 · What the phone sees subprocess

Session list pushed every 5 s; the selected session's transcript is polled at 1.5 s (initial tail capped at 512 KiB) and classified with the same transcripts.cjs machinery the desktop uses (webRemote.cjs:519-651). When an assistant turn completes, a Haiku summary is generated for the small screen — "2 sentences max + up to 3 action items", last 24,000 chars as input, skipped entirely when the turn is under 280 chars (webRemote.cjs:729-829, model claude-haiku-4-5 pinned).

4 · Security posture electron main

  • Command tiers (ipcSchemas.cjs:412-445): ungated reads (app:version) → SAS-gated reads (sessions, schedule, history) → mutates (save, pty input, schedule writes) which need BOTH the desktop kill-switch remoteControlEnabled=true (default false) AND state === 'authenticated' (webRemote.cjs:1003-1018). Out of the box the phone is read-only.
  • Opaque rejections: every failure goes over the wire as just {error: 'rejected'} — the detailed reason lands only in the local audit log, so a probing attacker gets no oracle (webRemote.cjs:992-1028).
  • Audit log: ~/.claude/session-manager/logs/remote-audit-YYYY-MM-DD.log (0600) — type, deviceId, msgId, result; never tokens or payloads (webRemote.cjs:244-262). Last 100 lines viewable in the tab.
  • Rate limits (relay-side): 100 cmds/min per device, 60/min per browser, OTP generation 10/hour.
  • Panic button: revokeAll() drops every paired device at once.
