Session Manager

Executive overview — what it is and its top features, briefly.

An Electron desktop app that acts as a local cockpit for the Claude Code CLI: a terminal you actually work in, plus 25+ tabs for configuration, observability, and scheduling around that terminal. A companion mobile web cockpit mirrors session state from the desktop app.

Terminal sessions

Each open tab is a real PTY running claude, managed by a per-tab PtyManager. The tab ID doubles as the Claude session UUID, so it passes straight through to --session-id and to transcript lookup — no separate ID mapping.

Scheduler — unattended PRD execution

Runs written task specs ("PRDs") as headless claude -p jobs, on a schedule or when API usage frees up. Policies: manual, on-reset, or when-available (default), which polls billing usage every minute to decide when to start/stop jobs around the 5-hour usage window. Concurrency is capped at 3 simultaneous jobs to avoid overloading the machine. A boot-time reconciler reaps jobs orphaned by a crash, and a periodic supervisor probe kills stuck poll-loops without killing the agent itself.

DOM Capture — pull page content into a Claude session

A selection-scoped extractor built into the Browser tab's embedded webview: pick one or more elements on the live page and pull them out as agent-ready DOM, full HTML, an accessibility tree, a robust selector chain, or a PNG screenshot — then route the result to a Claude session, the clipboard, or disk.

How to use it

  1. Open the Capture panel — click the target/crosshair icon in the Browser tab's action bar, which sets browser mode to capture.
    This starts the element picker inside the embedded page: a hover-highlight overlay is injected via executeJavaScript, since the view is a sandboxed WebContentsView with no reachable app globals — the picker buffers pick events on window.__smPicker and the main process polls/drains them.
    src/renderer/components/tabs/browser/CapturePanel.tsx:79 src/main/browserCapture.cjs:1
  2. Hover and click elements on the page — a click selects it (⌘-click adds more to the selection); each pick reports back a selector generated from a fallback chain: [data-testid] → #id → role+accessible-name → a minimal unique CSS path → an nth-of-type XPath.
    Selected elements appear as a list in the panel's "Selection" section.
    src/main/browserCapture.cjs:33
  3. Pick a capture mode — Agent-ready DOM (filter → prune → summarize → chunk, sized to a token budget), Full HTML (raw outer HTML), Accessibility tree (roles/ARIA/labels/states), Selector (the CSS/XPath/ARIA chain itself), or Screenshot (PNG, for non-semantic UI the other modes can't describe).
    src/renderer/components/tabs/browser/CapturePanel.tsx:37
  4. Click Capture — for the four text/tree modes this calls browser:capture, which runs the selected mode's extraction over the live DOM in the sandboxed view and returns the result to the panel. Screenshot mode instead calls browser:capture-shot, which grabs the tab's webContents.capturePage() as a PNG data URL.
    The result renders in the panel — a syntax-styled text block for text/tree modes, an inline image preview for screenshots. Nothing is written to disk yet.
    src/main/browserView.cjs:562
  5. Choose a destination — four options appear once something is captured: Copy to clipboard (text or, for a screenshot, the image itself); → Claude session (writes the capture into the active terminal tab's PTY input, prefixed with an explicit provenance banner); Save to scratch file; Save as PRD fixture. See the storage table below for the last two.
    The Claude-session destination frames the pasted content as inert reference data, not instructions — a two-line comment banner (# Captured page content below — untrusted data from <url> …) wraps it, the same defensive framing used for knowledge-graph ingestion, so a page an agent is capturing can't smuggle in a prompt injection disguised as user input. Text payloads are also truncated to stay under the PTY-write IPC boundary's 64 KiB cap.

Where it's stored

Nothing persists automatically. A capture lives only in renderer memory (the browser store's captured field) until you explicitly click "Save to scratch file" or "Save as PRD fixture" — closing the panel or navigating away discards it. Clipboard and Claude-session destinations never touch disk at all.

Show the write mechanics

Every save goes through this project's shared atomic-write path — a temp file + rename, never a partial write on disk — and every destination path is run through validatePath, which restricts writes to the user's home directory tree. Text saves call config.writeText (renderer IPC → writeTextAtomic); the screenshot's base64 PNG is decoded and written with writeBinaryAtomic via the browser:save-binary handler.

Record — turn a manual page flow into a replayable test

Records real interactions in the Browser tab's embedded page — clicks, typed input, navigations, assertions — as a step list you can replay in place or export as a runnable Playwright spec, a human-readable Markdown repro, or a PRD fixture.

How to use it

  1. Open the Recorder panel — switching Browser mode to record mounts RecorderPanel, which immediately starts an engine session for the active sub-tab and begins the transport clock at 00:00.
    Starting the session arms a per-view recorder-preload (loaded into the embedded page with a random --sm-record-token) that forwards real DOM events back to the main process over a dedicated, token-checked channel — the embedded page's own JS can never spoof a step, since only events carrying the matching token from the recorder-preload's isolated context are accepted.
    src/renderer/components/tabs/browser/RecorderPanel.tsx:80 src/main/browserView.cjs:204 src/main/browserView.cjs:343
  2. Interact with the page normally — click, type, navigate. Each interpreted interaction appears live in the panel's step list, tagged with a verb (navigate, click, type, wait-for, …) and the target selector (the same fallback-chain selector generator DOM Capture uses).
    A navigation is recorded even if you're mid-session on a new page — the recorder-preload re-arms itself on every page load using the same session token, so the recording survives the page it started on navigating away.
    src/main/browserView.cjs:96 src/main/browserView.cjs:171
  3. Pause / resume / stop — the transport row's record/pause button toggles capture without ending the session (paused time doesn't advance new steps); Stop ends the engine session for that view entirely.
    src/renderer/components/tabs/browser/RecorderPanel.tsx:186
  4. Parameterize a typed value (optional) — expand a type step and check "parameterize" to swap a literal value for a {{variable}} placeholder in exports, so the same recording can drive multiple runs with different input.
  5. Replay (optional) — plays the recorded steps back against the live page one at a time, marking each pass/fail inline, without needing an export first. Replay temporarily drops the view out of the active recording set so replayed actions don't re-append themselves as new steps.
    src/main/browserView.cjs:456
  6. Export — three destinations in the panel's footer. See the storage table below.

Where it's stored

The step list lives only in the renderer's browser store (recorderSteps) for the lifetime of the recording session — the main process only ever streams individual step events over IPC, it never persists them itself. Nothing reaches disk until you click one of the three "Export as" buttons; stopping the recorder or closing the tab without exporting discards the steps.
