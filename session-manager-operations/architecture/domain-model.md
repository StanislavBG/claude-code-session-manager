# Domain model (TAB / EPIC) — full reference

> Extracted from `CLAUDE.md` on 2026-08-24. CLAUDE.md holds the one-line laws; this file holds the
> rationale, incident history, and file-level detail behind each. Content below is verbatim from the
> CLAUDE.md section of the same name. **Read this before changing anything in the TAB→EPIC→PRD chain.**

The vocabulary for what grounds an Epic's session is **Agent** (an Agent Library persona — the
"who") **+ Tag** (the Epic's mission — the "what"), surfaced identically in the New Epic card,
Agent Library, and Tag Library — this is a current-terminology/UI update, not an API rename:
`PromptSession`'s `agentType`/`tag` fields, the `EpicTag` union, and "Epic" as the unit-of-work
noun are unchanged. Don't describe either library as read-only in new docs/copy — see their own
bullet below.

- **TAB = file location = Main Project.** A Terminal tab is anchored to one cwd; that cwd IS the project identity. Everything the app manages for a project keys off this path.
- **`<TAB cwd>/session-manager-operations/`** — the per-project operations root, created when a tab first opens on that cwd. Definitive path; session-manager owns and manages its contents (`scheduler/epics/<epic-id>/prds/`, `scheduler/state/`, `prompt-sessions/`, `HUMAN_LEARN/`, …).
- **EPIC = one small unit of work within the Main Project.** Implemented as `PromptSession` (`state/promptSessions.ts`). Each Epic carries an initial intent tag (**feature / bug / discussion** — expected to gain more clarity/kinds over time) and its `goalText`. The tag also sets how eagerly `/develop` should fire inside that Epic's session — see the `session-manager-dev:develop` skill's "Tag-aware default": `feature`/`bug` treat PRD decomposition as the expected next step, `discussion` keeps `/develop` available but never assumed until whether-to-build is actually settled.
- **New Epic creation is two independent selections, not one.** `agentType` (who runs the session — an Agent Library persona, `~/.claude/agents/*.md`, edited in the `AgentLibrary.tsx` list+detail editor) and `tag` (the Epic's **mission** — what it's for; its 5-tag taxonomy is a closed union and stays fixed, but `TagLibrary.tsx` is no longer read-only either) are separate axes on `PromptSession`. Neither library is a plain read-only directory any more: `AgentLibrary.tsx` is a full CRUD editor (New/Duplicate/Save/Revert/Delete, plus dropping a project's local overlay) writing straight to `~/.claude/agents/<name>.md` via `agentLibrary.cjs`'s `savePersona`/`deletePersona`/`removeOverride`, and each persona now carries a `tags:` frontmatter field (`AgentPersona.tags`) recording which of `TAG_LIBRARY`'s tags it's associated with — a many-to-many membership editable from either page (`AgentLibrary.tsx`'s tag-assignment chips, or `TagLibrary.tsx`'s "agents carrying this tag" list), both writing through the same `savePersona` call so the relationship has one source of truth regardless of which side you edit it from. Both field names are chosen to match this app's existing global vocabulary rather than inventing new ones: `tag` is the same field `lib/tagLibrary.ts`'s `TAG_LIBRARY`/`lib/agentTagDefs.ts`'s `AGENT_TAG_DEFS` already describe (never a second, drifted copy of a tag's mission text — every "what does this tag mean" string reads through `agentTagDef(tag).description`), and `agentType` reuses the exact field name Claude Code's own hook payloads (`SubagentStart`/`SubagentStop`'s `agent_type`), the Task tool's own `subagent_type` parameter (tracked as `subagentType` in `state/live.ts`'s `ToolUseTrace`), and a Team member's persona field in `teams.cjs` (`agentType`) all already use for "which persona is this" — not a fourth name for the same concept. `NewEpicCard.tsx` renders them as two side-by-side columns — "1 · Agent — who is working" (a real button list from `window.api.agents.listPersonas()`, defaulting to "Default") beside "2 · Mission — how they work" (the feature/bug/discussion pills, previously mislabeled "Type") — so it's visually obvious two different pickers are being set, not one. `lib/epicIntake.ts`'s `composeEpicIntake` folds the chosen persona's name+description into `openingPrompt` (never `goalText`) as a framing line that comes before the tag's own grounding template — the "who" is read before the "what". `agentType` folds into `openingPrompt` as described above, and now also sets the launched process's `--model` default for both views of that Epic's session: the chosen persona's own `model` frontmatter field wins when set and isn't `'inherit'`, else it falls back to the existing global default. `chatRunner.cjs`'s headless Chat launch resolves this via `src/main/lib/agentModelResolve.cjs`'s `resolveEpicModel` (main-process, falls back to `sonnet`); `EpicTerminalPane.tsx`'s Terminal launch mirrors the same persona-first logic renderer-side (its own `resolveEpicModel`, falling back to the raw-session-model toggle) since it can't import a `.cjs` main module — so Terminal and Chat agree on which model that session runs with even though the fallback literal differs per view. Beyond `--model`, `agentType` stays display-only — it does not otherwise change which claude CLI process spawns. An "advanced" toggle in the card header flips it (real CSS 3D flip, `rotateY`) to a read-only **grounding board** — `lib/groundingBoard.ts`'s `computeGroundingBoard` inventories the real System (`~/.claude/`) / Project (`<cwd>/`) / Local context this Epic's session will actually load (CLAUDE.md files, skills, mcp servers, hooks, the selected persona's own file, git branch, open Terminal tabs, other Epics in the project) via `window.api.config.*` reads — never fabricated placeholder numbers. It has no toggle-what-loads controls: session-manager cannot tell the `claude` CLI to skip a file it would otherwise discover on disk, so the board is deliberately an inspector, not a control.
- **"Sessions" is the user-facing name; `Epic`/`PromptSession` stay the code name.** Every UI surface (nav item, queue header, New Session card, empty states, Home/Scheduler copy) says *session* — that IS what an Epic is, a tagged claude session opened through AIM. This is a copy/label change only: `PromptSession`, `EpicTag`, `epicId`, every `epic-*` testid and every on-disk path (`scheduler/epics/<epic-id>/`) are unchanged, exactly like the earlier Agent+Tag terminology pass. Don't "finish" the rename into identifiers.
- **An ACTION is an Agent persona given a project scope — not a fourth concept.** A persona carrying `projects:` (project cwds, or the `*` sentinel = every project) plus an `action:` opening instruction and optional `actionLabel:` in `~/.claude/agents/<name>.md` renders as its own button in that project's Sessions toolbar (`components/epics/SessionActionsBar.tsx`; resolution is pure in `lib/projectActions.ts`, loaded live off `agents:changed` by `lib/useProjectActions.ts`). Pressing it is the same act as pressing "+ New Session": it goes through the one IPC handler holding `MINT_AUTHORITY_NEW_EPIC_UI`, composes through `composeEpicIntake` (persona = **Actor**, its first `TAG_LIBRARY`-ordered tag = **Mission**, the `action:` text = the goal), approves out of `proposed`, and sends. It is a shortcut around the New Session card, never a second creation path, and the SINGLE-CREATOR LAW is untouched — a human still presses the button. Scope lives on the persona file itself so there's no per-project registry to drift against; `agentLibrary.cjs` owns the three frontmatter fields (`action:` is newline-escaped because the frontmatter parser is line-based) and Agent Library edits them. The `builder` persona is deliberately excluded from the dynamic list: the Build button is already its Action, with publish-target gating and in-flight dedup a generic Action can't express. That button has **three faces, decided in `lib/buildAction.ts`** (pure; `SessionActionsBar` just renders the label it's handed): **Run Build** when `buildTarget.cjs` resolves a target, **Open Build** when a non-completed `build`-tagged Epic already exists for the cwd, and **Set Up Build** when the resolver returns `null`. `null` means *not configured yet*, **never** *cannot be built* — it is the state every non-npm project starts in, since the resolver only auto-discovers npm. So it stays **enabled** and mints a `build`-tagged Epic on a *bootstrap* goal (`BUILD_SETUP_GOAL_TEXT`): probe the project read-only, write `session-manager-operations/architecture/build-target.json` plus the project-local `.claude/agents/builder.md` overlay, then **stop for human approval** — it never invokes `/builder`, because writing a build target and immediately releasing against it is the accidental-`npm publish` this gate exists to prevent. The resolver stays deliberately **dumb** (does a config exist? yes/no) rather than growing a `pyproject.toml`/`Cargo.toml`/`go.mod` sniffer: an ecosystem list in the main process always lags reality, file existence yields no publish commands, and judgment-shaped answers ("bump `VERSION`, tag, flag that the live server needs a restart") only come from reading CLAUDE.md + git history — so discovery lives in the agent. Only "no project tab" and "lookup still in flight" actually disable the button; see [`architecture/build-target.md`](session-manager-operations/architecture/build-target.md) for the file's schema and a worked non-npm example. **Every Action is its own button** — the old single "Actions" dropdown is gone. The buttons are the Sessions pane's **Hot keys** section, and that pane has exactly **two sections and no third band of chrome**: Hot keys, then the sessions widget (`epic-queue-hotkeys` / `epic-queue-widget`). Filtering is the *widget's own head bar* — title + count + controls drawn inside the widget, on top of the tiles it governs, never a slab of pane furniture between the two. Within that head bar, status/group/sort are **three peer dropdowns** ("show / group / sort", `EpicQueueControls`'s `MiniSelect`), status defaulting to `open`; it used to be five counted `FilterPills` that wrapped to two lines in a 352px pane for a control that only ever holds one value, so the counts moved into the option labels (`Open 3`, `All 94`) and nothing was lost. Only search (an input) and row density (an icon) stay behind toggles — there is no separate options/hamburger menu any more.
- **The Epic's opening prompt is built from the AIM framework — Actor, Input, Mission, in that order — and all three get an explicit line, not just two.** Actor = the chosen `agentType` persona (`You are acting as the "<name>" agent: <description>`). Input = what's grounding the session, stated via `lib/groundingBoard.ts`'s `summarizeGroundingBoard(groups)` — a pure, no-extra-IO summary of the same real System/Project/Local inventory the grounding board UI already computed (`board` state if "advanced" was opened; computed fresh via `computeGroundingBoard` at submit time otherwise, in `NewEpicCard.tsx`'s `handleCreate` — never a second fetch path). Mission = the tag's `initialPromptTemplate`, followed by the human's own goal text. `lib/epicIntake.ts`'s `composeEpicIntake` composes exactly this order (`agentName`/`agentDescription` → `inputSummary` → `tag` → `goal`) into `openingPrompt`; each of the three inputs is independently optional and simply omits its line when absent — callers that never ground an Epic against a real project (e.g. `EpicQueue.tsx`'s scripted 'build' Epic) still work, they just carry a thinner prompt. This is deliberately still just a *framing line*, same status as the Actor line it sits beside — Input stays real-data-derived and display-only, never fabricated, and never a second source of truth for what the `claude` CLI itself loads.
- **Settings (System/Project/Local scopes) is substrate, not per-Epic curation — never confuse the two.** `Settings.tsx` (and its siblings Permissions/Hooks/MCP Servers/Skills) edits on-disk `settings.json`/`.claude/` files at exactly three file-level scopes (`lib/scopes.ts`'s `SETTINGS_SCOPES`: `~/.claude/settings.json` user, `<cwd>/.claude/settings.json` project, `<cwd>/.claude/settings.local.json` local) — the same files the `claude` CLI itself reads from disk on *every* invocation it launches, identically, regardless of which Epic. It was never scoped to "one session" in the old TAB=session model either; that model just made the distinction invisible because a TAB's one session and its one project settings.json had matching lifetimes. Now that one TAB hosts many EPICs, a Settings edit at Project scope changes the substrate for **every current and future Epic in that project** (User scope: every Epic machine-wide) — Settings holds no per-Epic override for most fields, and `groundingBoard.ts` only *reports* that these files exist (`inputSummary`'s one-line mention) rather than injecting their content. The per-Epic curation layer is Agent + Tag, not Settings: `agentType` (Actor) and `tag` (Mission) are folded into `openingPrompt` fresh at that one Epic's creation via `composeEpicIntake` (see the AIM bullet above) — that's the only place "how this specific Epic should work" belongs. **`model` is the one Settings-adjacent field carved out per-Epic, not per-scope**: `agent-model-default-terminal`/`agent-model-default-chat` wired `src/main/lib/agentModelResolve.cjs` so the chosen persona's own `model` frontmatter field sets the `--model` a given Epic's session launches with (falling back to Settings' "Model & Reasoning" default only when the persona has none or is `'inherit'`) — see the AIM bullet above. Every *other* field in Settings' "Model & Reasoning" group — `effortLevel`, `fastMode`, `alwaysThinkingEnabled`, and the rest — remains substrate-only with no per-Epic override: no `--effort` flag or equivalent exists in this codebase's `claude` CLI invocations today, so those stay a known gap for a future PRD once a real CLI mechanism is confirmed, not something the Agent persona can already carry. **Rule: if a behavior should differ per Epic or per task, it is a new/edited Tag (`TagLibrary.tsx`'s `initialPromptTemplate`), a new/edited Agent persona (`AgentLibrary.tsx`'s persona file, including its `model` field), or, for reasoning/effort settings specifically, a future PRD — never a plain Settings edit.** Settings otherwise holds what's legitimately identical for that scope regardless of task: permissions, hooks, MCP servers, env vars, output style, and (pending that future PRD) default effort/reasoning mode. If a user wants "this kind of task to run with a different settings.json," the correct lever today is authoring a custom Tag or a custom Agent (model included), not touching Settings. **`SystemPrompt.tsx` is the one scoped editor carved down to User scope only** (2026-08-08): it edits `~/.claude/CLAUDE.md` and nothing else. It is a HOME-face screen, where there is no project context, so its old User/Project/Local switcher could only dead-end ("no active project") or silently point at whichever project owned the active top tab — and `<cwd>/CLAUDE.md` / `<cwd>/CLAUDE.local.md` are contextual to a project, discovered by the CLI from the session's own cwd at invocation. Don't re-add the switcher there; the other scoped editors (Settings, Permissions, Hooks, MCP Servers, Skills) keep all three scopes. That screen is also a **document set, rendered through the app's own document view**: `~/.claude/CLAUDE.md` plus every file it `@`-imports are listed in a left rail (`ReferencedFilesPanel`, now selection-only) and the selected one opens in `components/tabs/editor/DocumentEditorPane.tsx` — the Edit/Preview/Split + markdown toolbar + outline + word-count chrome extracted out of `EditorView` so no screen has to re-implement it around a bare `MarkdownEditor` again. Imports are **editable** there through the same dirty-tracked config store and the same SaveBar as the root file (they are literally part of the prompt the CLI loads); only an import that doesn't resolve is read-only. `DocumentEditorPane` deliberately omits the Document Experience popover / Assistant rail — those spawn a background claude session via `useDocEdit`, a cost `EditorView` opts into explicitly and a config screen must not inherit. Per `agent-model-nav-consolidation`, Settings' curated "Model & Reasoning" card is demoted to advanced/raw-JSON-only (out of the default Guided/Tree view) since its one per-Epic-wired field, `model`, is now edited from Agent Library's persona detail editor instead — `effortLevel`/`fastMode`/`fastModePerSessionOptIn`/`alwaysThinkingEnabled`/`availableModels`/`modelOverrides` are still Settings-only, just reachable via "show advanced" now rather than the default view.
- **An Epic's title + objective are fixed for the life of its session, and are its first prompt.** The New Epic card composes both through `lib/epicIntake.ts` and sends the objective into the Epic's session at creation — the Epic opens with the agent already working, and nothing rewrites `goalText` afterwards (iteration happens in follow-up messages). One short-lived Epic per unit of work is the intended shape; don't mutate an Epic's goal to repurpose it, start a new one. The queue row menu's rename action (`renameEpic` in `state/promptSessions.ts`) is a narrow carve-out to this: a cosmetic title/goal-text correction (typo, clarity), never a re-purposing of what the Epic is for.
- **An Epic's lifecycle is its single `status` field, specified in [`prompt-sessions/README.md`](session-manager-operations/prompt-sessions/README.md#lifecycle).** That section is the functional requirement. Exactly three states — `proposed` (not started: an agent asking, OR a human still composing), `active` (session running, authoring PRDs, receiving scheduler updates), `completed` (archived). There is no `draft` state; a half-typed Epic is `proposed`. **Every Epic is born `proposed`; nothing is created directly as `active`.** One transition `proposed → active`, reached either by **Approve & start** or by submitting the first prompt in the New Epic flow — that submit IS the transition, not a second kind of creation. A `proposed` Epic is a valid minimal row (`id` + `claudeSessionId` are enough — reserved and ready to spawn; goalText/openingPrompt fill in later) and is **never erased**; only `markCompleted` removes it, by archiving it, or `deleteEpic` (queue row menu, `state/promptSessions.ts`) hard-removes it with no archive — guarded to refuse a live scheduler job/chat run/attached Terminal session. Only the persisted `status` may be shown as the Epic's state — run activity is **session** state, not Epic state. Three entities own their own properties: **EPIC** controls the session, **SESSION** writes the PRDs, **PRD** carries its own. New tracking/display fields go on the entity whose lifecycle they share. Don't restate any of this elsewhere; link there.
- **An Epic is created in exactly ONE place: the human pressing New Epic** — plus one narrow, deliberately-argued second door for **inbound cross-project feedback** (next bullet). This is the SINGLE-CREATOR LAW, enforced fail-closed in `src/main/lib/epicMint.cjs` — `ensureEpic()` is join-only for every caller except `lib/promptSessionsCreateEpic.cjs` (the New Epic card's IPC handler), which is the sole holder of `MINT_AUTHORITY_NEW_EPIC_UI`, and `lib/crossProjectFeedback.cjs`, the sole holder of `MINT_AUTHORITY_CROSS_PROJECT_FEEDBACK` (`MINT_AUTHORITIES` is the full, two-entry list — a third entry is a domain-model change, not a convenience); anyone else asking for an Epic that doesn't exist gets a throw plus an `epic_mint_refused` audit event. There is no agent-facing proposal channel: `/propose-epic`, `scripts/propose-epic.cjs`, the RCA hook's auto-filed Epics and the watchdog's feedback sweep are all **removed (2026-08-02)**, as `/process-feedback` + `/my-feedback` and `session-manager-operations/feedback/` were before them (historical contents archived to `feedback/archived-2026-08-02/`). An agent that is sure work is needed runs **`/develop`** inside the Epic it is already in — PRDs join an existing Epic, they never conjure one. An agent that is not sure says so and lets the human open an Epic. `status: 'proposed'` remains the birth state of every Epic and the gate before anything runs: nothing is spent until someone presses **Approve & start** (`EpicApprovalBar`), which sends its `openingPrompt` (falling back to `goalText`) as the session's first message.
- **Project-to-project feedback goes through Session Manager, as a `proposed` session in the RECEIVING project.** With `/process-feedback` / `/my-feedback` / `feedback/` retired (2026-08-02) and the scheduler correctly locked to join-only, an agent in Project-A had no way to hand a finding to Project-B. `src/main/lib/crossProjectFeedback.cjs` is that conduit and the ONLY one: the app's main process is the single process legitimately holding several projects' operations roots open, so it performs the cross-folder write. Surface: the `feedback_open_session` / `feedback_list_projects` MCP tools (`scripts/scheduler-mcp-server.cjs` → `POST /admin/feedback/open-session`, `GET /admin/feedback/targets`), with the `session-manager-dev:send-feedback` skill making the flow explicit. **What lands is a `proposed` Epic in Project-B's own queue and nothing more** — the BORN-PROPOSED check applies to this mint authority verbatim, so a human in the *receiving* project is still the one who spends anything by pressing **Approve & start**. This is NOT a reopening of the removed agent-facing proposal channel: that channel let an agent file work into the project it was already running in, which `/develop`-inside-your-own-Epic replaced and which stays refused — `toCwd === fromCwd` is rejected outright and the error names `/develop`. Other fail-closed guards: both cwds through `validatePath`, both must be real directories, and the target must ALREADY have a `session-manager-operations/` dir (this module never conjures an ops root in an arbitrary directory). Provenance rides on the Epic itself (`EpicSource.producer: 'cross-project-feedback'` + `fromCwd`/`fromEpicId`) — there is no cross-project registry anywhere — and `lib/epicOrigin.ts` reads it into the queue-row / approval-bar chip so the receiving human sees the claim came from an agent that never read their codebase. There is no reply channel and no callback: when the sending Epic is resolvable, a receipt event is chained onto it and that is the whole loop.

- **A scheduler job's question comes back to the session that wrote the PRD.** A job parked in `needs_review` is a question, not a result. `lib/rcaReport.cjs` writes a deterministic root-cause report next to the run's own log (`runs/<runId>/root-cause-<slug>.md`, mirroring the DoD gate) and `scheduler.cjs`'s `notifyNeedsReview` appends it as a `response` event on the AUTHORING Epic's chain, resolved from the PRD's `sourcePromptId` (falling back to the job's `epicId`) — the same channel `notifyOriginatingTab` uses for completed/failed. Join-only: if no open authoring Epic exists, the report + the Scheduler tab are the whole record. This is also why PRDs must be written to the point: the clearer the PRD, the less there is to route back.
- **EPIC : claude-session = 1:1 — an Epic IS a tagged claude session.** Each Epic mints its own `claudeSessionId` (never shared with or derived from any SessionTab's sessionId), and the Epics list is the user's list of tagged sessions they iterate in. **Chat and Terminal are two VIEWS over that one session, never two sessions**: Chat = headless `claude -p --resume <claudeSessionId>` via chatRunner; Terminal = interactive PTY `claude --resume <claudeSessionId>` in the Epic's cwd. Switching views must hand off the session (mutually exclusive attachment), not mint a new sessionId — context continuity across the switch is the invariant. The Epic is the context root for that session; `EpicDetail.tsx`/`EpicComposer.tsx` render the claude session *in the Epic's context* on screen. Its event chain (`prompt → prd_created → response → closed`, FK-linked via `causedByEventId`) is the auditable trace of everything the Epic spawned, including PRD-dispatch chips. **By default, an active Epic's session runs inside its own isolated `git worktree`** (branch `sm-epic/<id>`, `src/main/lib/gitWorktree.cjs`'s `createEpicWorktree`, created at the `proposed → active` transition) rather than the project's shared working tree, so concurrent Epics on one project stop clobbering each other's uncommitted edits — both the Terminal PTY and headless Chat spawn cwd resolve to it (`epicSpawnCwd.cjs`). That isolation resolves back into the shared tree at exactly one checkpoint, never mid-session: an explicit "Merge to main" action or `markCompleted`'s merge-before-archive step (`lib/epicWorktreeMerge.cjs`'s `integrateEpicBranch`, ff-only → merge-commit → abort-and-flag). A real conflict sets the Epic's `worktree.status` to `needs_merge_resolution` (surfaced as EpicDetail's conflict banner, with a "Resolve in Terminal" affordance into the same worktree dir) rather than blocking anything — see `epic-primitives.tsx`'s `EpicWorktreeChip` for the on-screen isolation-state readout, and Settings' project scope for the per-project opt-out.
- Persistence: active Epics in `session-manager-operations/prompt-sessions/active-index.json`; completed ones archived one JSON per Epic in the same folder (`promptSessionArchivePath`). An archived Epic's claudeSessionId is dead — resuming mints a new session with `resumedFromId` tracing back.

- **Scheduler = a browser over TAB → EPIC → PRD** (implemented 2026-07-31, v0.39.4). The Scheduler tab is a viewer/operator surface on this hierarchy — scoped to the active TAB's project by default ("All projects" is the explicit machine-wide escape hatch). Its nav row is **PROJECT-face only** (`navGroups.ts`, 2026-08-08): every route it renders is cwd-derived, so a Home-face copy could only have shown the federated all-projects view — cross-project queue monitoring is deliberately postponed rather than built as a federation layer. Home still *reports* queue state (the Queued card, the Needs-you "View in Scheduler" row, the footer's paused pill); those links route through `openPanel`, which now asserts `navFace: 'project'` for any PROJECT-only NavKey (`isProjectOnlyNavKey`) so they can't strand you on a project-scoped screen with the Home sidebar. On disk, per project: PRD sources in `scheduler/epics/<epic-id>/prds/` (every new PRD auto-mints/joins an Epic via `lib/epicMint.cjs` — flat `scheduler/prds/` is RETIRED and auto-consolidated into `prds-archived/` at the top of every `reconcile()` pass, not just at boot — `consolidateAllFlatPrds` runs from inside `reconcile()` itself (every one of its callers: tick-queue poll, job completion, `schedule:state`/`schedule:rescan`, `rescheduleTimer`) before `reconcile` scans that dir, so a file dropped there while the app is already running is swept before it could ever become a queue row), queue + history shards in `scheduler/state/` (`lib/queueStore.cjs`). Global bookkeeping is retired; what remains machine-level is Session-Manager runtime only: `~/.claude/session-manager/scheduler-machine.json` (policy/pause), run logs under `scheduled-plans/runs/`, and the **session slot pool** (`lib/sessionSlots.cjs`) — one machine-wide pool of ≤3 concurrent `claude -p` sessions that scheduler jobs AND chat runs must acquire from. Surfaced in the "Session-Manager" Configure nav tab + the Home "Active sessions" widget. **PRD authoring is API-only**: the `scheduler_create_prd` MCP tool (`mcp__session-manager-scheduler__scheduler_create_prd`) is the sole sanctioned way to write a PRD file — it validates frontmatter, atomically allocates `NN`, and enforces the Epic-join rule below. Hand-writing a PRD file directly (the `/develop` skill's `mint-epic.cjs` fallback) is a degraded last resort only for when the app isn't running, and any agent using it must say so visibly in its report; `scripts/audit-ops-hygiene.cjs` and the `ops-sweep` skill independently flag a hand-written PRD they find as a hygiene finding.
- **One TAB per project.** The sidebar button is "Open / Start Project" (native folder picker; New Folder = start). Picking an already-open project activates its existing tab — extra sessions within a project are Epics, not tabs.

- **Single-writer law over the operations root** (`src/main/lib/opsOwnership.cjs`). Every `session-manager-operations/<namespace>/` folder has exactly ONE owning surface that may write it; everyone else reads freely. Owners today: `prompt-sessions → epics`, `scheduler → scheduler`, `project-brief → project-home`, `logs → logs`, `bilko-host → bilko-host`. It is **fail-closed** — a write by an undeclared writer, or into a namespace with no declared owner, throws. Every write path enforces it (`config.cjs`'s `writeTextAtomic`/`writeBinaryAtomic`/`writeJson`/`writeJsonSync` via `opts.writer`, plus `lib/epicMint.cjs` and `lib/queueStore.cjs`, which use raw `fs`). Renderer callers declare theirs through the IPC payload (`config.writeJson(path, data, 'epics')`). Cross-writer exceptions are narrow, path-scoped **delegations** declared in one table — today only the scheduler writing `prompt-sessions/active-index.json`. Adding a namespace or writer is a deliberate edit to that file, not an implicit consequence of calling `fs.writeFile`. Each `OWNERS` namespace has its own `README.md` at its folder root (`prompt-sessions/README.md`, `scheduler/README.md`, `project-brief/README.md`, `logs/README.md`, `bilko-host/README.md`) documenting its on-disk shape, sole writer, and lifecycle — read the namespace's README before writing code that touches it.
- **No "general" OWNERS namespace exists, and none is needed right now (decided 2026-07-31).** `architecture/`, `design-mocks/`, `HUMAN_LEARN/`, `manual/` (source of the **paid** Field Manual — see its own README; built into `~/Projects/Bilko/data/manual/releases/<version>/` by `scripts/build-manual.mjs`, sold at bilko.run/manual for $19.99 on the already-live `session_manager` SKU. **This project is open-core: the APP is free and stays free — the manual is the only paid artifact.** Never add a license check, entitlement gate, trial limit, nag, or "pro" tier to the app itself, and never move an existing app feature behind a purchase; the business model is deliberately "free tool, paid knowledge", the same shape many open-source projects fund themselves with. `MANUAL_PRODUCT_KEY` in `~/Projects/Bilko/shared/manual-catalog.ts` deliberately reuses the pre-existing `session_manager` purchase rather than minting a second SKU, so every past buyer already owns the manual — changing that strands them and is a human decision, not a refactor. `~/Projects/Bilko/tests/open-core-positioning.test.ts` guards the marketing copy against drifting back to "buy the app"), `reviews/`, `project-pages/`, `feedback/` (retired, see above), and `browser/` (artifact folder left over from the retired Browser tab — no OWNERS entry, no README, safe to delete on sight) also live under `session-manager-operations/` but are deliberately NOT in `OWNERS` — they are written directly by Claude Code skills (e.g. `explain-to-me` writes `HUMAN_LEARN/`) via the `Write` tool, outside the app's own IPC-mediated write path, which is why `assertOpsWrite`'s fail-closed check doesn't (and isn't meant to) block them: that check only guards `config.cjs`'s own write helpers and the two raw-`fs` modules (`epicMint.cjs`, `queueStore.cjs`), not arbitrary filesystem writes by tooling. This is the correct split, not a gap: `OWNERS` governs *app-owned runtime state* (Epics, PRDs/queue, the Brief) where two writers racing would corrupt a JSON source of truth the app reads back every session; the skill-authored folders are *documentation/artifact* output with a single human-or-agent author per invocation and no concurrent-write hazard to guard against. Revisit only if a genuine cross-cutting, non-tab-specific *runtime* write need appears with no existing namespace to hold it — don't add a speculative `general` namespace ahead of that. Any new top-level folder under `session-manager-operations/` must land in this enumeration or in `OWNERS` in the same PR that creates it — see `session-manager-operations/architecture/ops-maintenance-protocol.md` for the drift this causes when skipped (its Pattern A found this exact enumeration out of date and `feedback/`'s retirement status contradicted between two bullets in this very file — both now resolved).

Any new feature touching sessions, navigation, or per-project state must map onto this TAB→operations-root→EPIC→session hierarchy rather than inventing a parallel scoping scheme.
