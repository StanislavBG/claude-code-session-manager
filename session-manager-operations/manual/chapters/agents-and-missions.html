Shaping your team — Agents, Missions and one-click Actions

Every agent in your agency is just a plain text file — no coding needed to write one. This chapter shows you how to write your own, pick a Mission for it, and turn your favorite setup into a single button.

Write an agent in plain English

On Home, open Agents from the sidebar. Its Personas tab lists the agents already on your machine — the architect, the dev-leads, and any others you've added. Each one is a small text file with a few labeled parts, called fields. You fill them in, and the agent is ready to work.

  • name — the file's short label, all lowercase with hyphens, like release-notes-writer.
  • description — one sentence saying what this agent does. It shows up in every list where you pick an agent, and it's read aloud to the agent itself at the start of a Session, so write it like an instruction, not a title.
  • instructions — the longer text below the fields. This is the agent's own rulebook: what it should always do, what it should never do, and how it should think about the work.
  • model — optional. Leave it blank and the agent uses whatever the Session would use anyway. Set it and every Session that hires this agent uses that model instead.

Here's a short example — an agent whose only job is turning a list of changes into a friendly note for users:

---
name: release-notes-writer
description: Turns a list of finished changes into a short, friendly note for users.
model: sonnet
---

You write release notes for our users. Keep each note to two or three
sentences. Say what changed and why it helps them, and skip any detail
they'll never see.

A good agent has a description that reads like a real instruction, not a job title, and instructions that are specific enough to remove guesswork. "Write good code" tells an agent nothing it doesn't already assume. "Never touch a test file unless the test itself is wrong" tells it something it can actually follow.

Think of it like this: the Agents page is your agency's staffing directory. Every entry is a job description you write once. Any Session can hire that person for the work, and the description you wrote is the first thing they read before starting.

Picking a model — and what it costs

Session Manager offers a small set of models: Haiku, Sonnet, Opus, and Fable, plus the "match my Session" option that leaves the choice to whatever's already running. They aren't interchangeable on price. Haiku is the cheapest and fastest. Opus is the most capable and the most expensive per exchange. Sonnet sits in the middle and is the sensible everyday pick.

The rule of thumb built into the Agents page itself is blunt: give a cheap model to an agent that only reads files and reports back, and save the expensive model for an agent that has to make real judgment calls — deciding what's broken, or what approach is safest.

Try this: open an agent you already have, and check its model field. If it's blank, that agent is quietly inheriting whatever model its Session happens to use — which may be pricier than the work needs.

Your copy, or the project's copy

An agent you write lives on your machine and works in every project you open — it's your personal copy. But one project can keep its own small override of that same agent, changing only its model, without touching the version everyone else sees. That's useful when one project's work is genuinely heavier or lighter than usual, without renaming the agent or making a second one.

Missions — what kind of work a Session is

Every Session carries exactly one Mission, alongside its Agent. Where the Agent answers "who's doing this work," the Mission answers "what kind of work is it." You can see the full list of Missions on the Agents page, in its Tags tab.

Three Missions show up as buttons when you start a Session by hand:

MissionWhat it sets up
FeaturePlans new work, then hands the actual building to the Scheduler as work orders.
BugReproduces the problem first, then queues a fix — never guesses at the cause from a description alone.
DiscussionKeeps the Session talk-only. No files change until you decide something is worth building.

A handful of other Missions exist behind specific buttons elsewhere in the app — publishing a release, or writing a project's overview page — and you'll never need to pick those by hand.

Each Mission carries its own short opening instruction, which the agent reads before your own goal. Discussion's, for example, tells the agent plainly that the point is a decision, not a code change. That's why swapping Missions changes how a Session behaves, even with the same goal typed in and the same agent doing the work.

The Tags tab is read-only. It shows each Mission, the opening instruction it carries, and the agents connected to it. To connect an agent to a Mission, open that agent on the Personas tab and click the Mission in its tags field. Click it again to remove it.

Why only there? The connection is saved inside the agent's own file, so the agent is the one place to change it — click an agent's name on the Tags tab and you land right on it. What you can't do is invent a brand-new Mission from the app itself. The built-in list is fixed on purpose, so it stays small and every Session means the same thing by "Feature" or "Bug."

The Agents tab — roster and character sheet

The Agents tab lists every agent as a character. On the left is the roster, with a Filter agents box, a Global / In project scope switch, and a button to collapse or expand the list. Pick an agent and its sheet opens on the right: its name, description, Stats (model and effort), and where it is used (Epic chat, Scheduler jobs, Tasks). Edits show No unsaved changes or a Save prompt (Ctrl S), and Delete removes the agent.

Bundled agents and app updates

The agents that come with Session Manager arrive with app updates. Install the new npm release, then restart the app. At start, any agent you never edited updates itself. You don't need to do anything.

An agent you edited is kept as it is. Its sheet in the Agent Library is marked newer version available, so you know it is behind. You have two choices:

  • Take the new version — the bundled agent replaces yours. Your old file is saved first in ~/.claude/session-manager/persona-backups/.
  • Keep mine — your edited agent stays. The notice goes quiet until the next bundled version comes out.

Gear and loadouts

Every agent has a loadout: what it may use. The roster shows it as a state. Undecided means nobody chose yet, so it runs with everything. Bare means no extra tools at all, only the floor no agent can drop. Equipped means exactly the tools listed. Unbound means every tool on this machine, MCP servers added later included, chosen on purpose.

A scheduled job's agent gets the MCP servers its persona declares, as long as they are set up in Claude Code for that project or for you. A server that holds a secret in its settings is not handed to a job, and the scheduler warns you when you queue a plan whose agent names a server the job could not load. Changing a plan's agent re-pins the job to the new agent.

The sheet has two panels. Gear holds the loadout: Built-in tools, MCP servers and Packs, plus the buttons Choose a loadout, Go bare, Go unbound and Open the Armory. Constraints shows what limits the agent: Always granted, Banned in unattended runs, Risk marks (READ, WRITE, MONEY, PUBLIC, IRREVERSIBLE) and the Sandbox environment.

The Armory

The Armory drawer lists everything Installed on this machine, with a search box. Each item is added either by dragging it onto the sheet (Release to equip) or by pressing Equip; Unequip takes it off. For an equipped MCP server, open its Powers to tick the individual tools it may use (All / None, shown as "n of m powers"); risky ones carry a badge.

First run and project overrides

An agent that is still Undecided shows Needs a decision first, and the sheet offers Choose a loadout (or Not now). A loadout is global by default. Choose a project under This loadout applies to to give the agent a different loadout for that project only; project edits save as you make them, it reads Same as global. until you change it, and Reset to global drops the override.

Changes apply to new sessions. The agent's gear applies to the chat too, so you can ask questions and troubleshoot with the same character that does the Session's work, and the same loadout governs scheduler jobs and Tasks. Skills only come inside packs: an agent can use a skill only if one of its packs carries it.

Actions — a favorite agent, one click away

Once an agent is written the way you like it, you can turn it into a button. Give the agent a project — one specific project, or every project — and a short opening instruction, and it appears as its own button in that project's Sessions toolbar, right next to "+ New Session."

Pressing that button isn't a shortcut around Sessions — it starts a brand-new one, the same way "+ New Session" does. It just skips the typing: the agent you scoped becomes the Session's Agent, its connected Mission becomes the Session's Mission, and the instruction you wrote becomes the opening goal. The button's label is the agent's name unless you give it a shorter one.

Project Video tools — a project's own video makers

A Project Video tool is the same kind of button, made for videos. It belongs to one project only. You'll find it in that project's Project Home, under Videos, and nowhere else. Other projects never see it.

Pressing it works like any Action: it starts one new Session, with the tool's agent, Mission and opening goal already filled in. The agent then builds the video for that project. A Voice menu beside the tool picks who narrates. Leave it on Default to use the agent's own voice; the Voices view in Videos lets you hear each choice first.

A tool can also ask for your review first. Then the agent stops halfway and saves a draft for you, such as the script and a storyboard picture. You check it in Project Home › Videos and click Approve or Ask for changes. No agent can make that choice for you. Only after you approve does the agent build and save the final video. If that approved final run fails, a Retry final run button appears so you can start it again.

Think of it like this: the review step is a sign-off on the storyboard. The crew doesn't shoot the film until the director says yes.

What you learned

  • An agent is a plain text file with a name, a description, instructions, and an optional model — no code required.
  • Models differ in price and power: cheap models for simple, read-only work; Opus for real judgment calls.
  • An agent lives on your machine by default; one project can override just its model without touching the shared copy.
  • A Mission sets what kind of work a Session is and what it reads before your goal; the built-in list is fixed, and you connect an agent to a Mission on the agent itself.
  • Scoping an agent to a project turns it into a one-click Action button — a shortcut to a normal new Session, never a second way to create one.
  • A Project Video tool belongs to one project and shows only in its Project Home › Videos; a tool with review waits for your approval before it saves the final video.
