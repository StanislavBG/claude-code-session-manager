House rules — instructions, settings and permissions

Tell every agent how you like things done, and decide what they may do without asking — without switching off the safety rails.

Claude Code reads a small set of files before it does anything else. Session Manager gives you an editor for each one. This chapter covers your machine-wide System Prompt, a project's own house rules and how agents share them, and the Settings and Permissions every Session obeys.

The System Prompt: your machine-wide house rules

On Home, the sidebar's CLAUDE.md row, under Claude Code, opens your System Prompt. It edits one real file: ~/.claude/CLAUDE.md. Every Session that Claude Code starts, in every project on this machine, reads this file first. Saving here changes what every agent knows before it reads your request.

This page has no scope switcher, because the file has no scope to switch. If the file uses @path/to/file.md-style imports to pull in other files, a left-hand rail lists each one so you can edit it too. They are part of the same instructions.

Think of it like this: the System Prompt is the handbook every new hire at your agency reads on day one, no matter which project they're assigned to. Change the handbook, and every future hire reads the new version.

A project's own house rules: CLAUDE.md

A single project can add its own rules on top of the machine-wide ones. Claude Code looks for a file named CLAUDE.md in the project's own folder, and a second file named CLAUDE.local.md for rules that apply only on this machine. Both are read fresh whenever a Session starts in that project.

To edit them, switch to that project's tab and open Claude config from the sidebar. It gathers the project's own Claude Code files in one place: Memory, CLAUDE.md, Settings, MCP, and Skills each get a tab. On the CLAUDE.md tab, choose Project to edit CLAUDE.md, or Local to edit CLAUDE.local.md.

CLAUDE.md is shared with everyone who works on the project; CLAUDE.local.md stays on your machine.

Good to know: your machine-wide file and a project's file share the name CLAUDE.md. The one you open from Home reaches every project. The one in Claude config reaches only its own project.

One map for every agent, and a tool to keep it tidy

A Session can run Codex or Gemini instead of Claude Code. Each tool looks for its own instructions file. If a project copies its rules into each one, the copies drift apart, and no agent can tell which one is true.

AGENTS.md: the shared entry map

The fix is one shared file, AGENTS.md, that holds the project's instructions: short rules, plus links to longer docs. Codex reads AGENTS.md on its own. Gemini normally reads only GEMINI.md, so Session Manager tells it to read AGENTS.md too.

Claude Code reads CLAUDE.md, and once a project has one, it skips AGENTS.md unless CLAUDE.md pulls it in. So the project's CLAUDE.md is a one-line stub: @AGENTS.md. That line imports the shared map. Anything below it is for Claude Code alone and never repeats the map. Any folder with its own notes uses the same pair.

Tools › Review MD network

Docs pile up and go stale. On a project's Project Home, the Tools tab has Review MD network. It scans the project's markdown files, the plain-text docs agents read, and draws how they link. Its idea is "write once, reference many": each fact lives in one doc, and other docs link to it.

The review sorts every doc into one of five kinds:

KindWhat it holds
MapThe top AGENTS.md or CLAUDE.md: one-line rules and links. Every Session loads it.
Folder notesA folder's own facts, never a copy of a top rule.
Topic docsThe one doc with a topic's full text.
Agent filesPersonas, skills, plugins and commands, loaded by name.
HistoryDated reports and logs. Never edited, never the current answer.

The FIX LIST card ranks what to repair. Copied text comes first, and each row names the doc that should keep it. Broken links come next, then orphans: docs the map never reaches. Each row has an Open button.

To go deeper, pick a Scope and a Mode, Full review or Drift check, and press Run review. That starts a Session with the architect. It reports first and changes no files until you approve.

Settings: three scopes, one winner

The Settings page, also under Claude Code, edits the preferences Claude Code keeps in a file called settings.json — environment variables, the default model, and other choices. There isn't just one copy of this file. There are three, one per scope:

ScopeFileApplies to
User~/.claude/settings.json Every project on this machine.
Project<project>/.claude/settings.json This project only. Meant to be shared with your team.
Local<project>/.claude/settings.local.json This project, this machine only. Never shared.

The Settings page on Home edits your User file. A project's Claude config page has a Settings tab where you pick Project or Local. It's the same editor either way.

When the same setting is written in more than one file, Local wins over Project, and Project wins over User. Settings opens on its General tab, which shows the value that will actually take effect for each setting, so you can check it before you change anything. Its Raw tab shows the whole file as plain text, for when you'd rather edit it by hand.

Good to know: Permissions, which we cover next, isn't a separate file at all. It's a section inside these same settings.json files, so it's a tab inside Settings rather than a page of its own. Hooks work the same way, with their own tab right next to it.

Permissions: fewer interruptions, same safety rails

By default, Claude Code stops and asks before doing anything risky — deleting a file, running an unfamiliar command, reaching outside your project folder. That's the safety rail, and the Permissions tab was never meant to remove it. What it does is let you tell Claude Code, once, which specific things are safe to do without asking again.

Permissions has three rule lists and one overall mode:

Rule listWhat it does
AllowSkips the prompt for anything matching the rule.
DenyBlocks anything matching the rule, no prompt, no override.
AskForces a prompt for anything matching the rule, even if it would otherwise be allowed.

Above the lists sits one bigger switch: the default mode, the agent's posture before any rule is checked. Options include the normal ask-when-unsure mode, a mode that accepts routine edits, a read-only planning mode, and a mode that skips permission checks entirely. Most people leave it on the normal, safest setting.

The Permissions tab shows the rules of one file at a time: the scope you're editing. Before you add a rule, glance at the other scopes too. A new rule can duplicate — or contradict — one that's already there.

Watch out: an Allow rule written at Project scope ships to everyone who works on that project the moment they pull your changes. A command you trust is not one your whole team should skip asking about. Keep personal rules at User or Local scope, and save Project scope for rules the team has agreed on.

Tool risk: a brake for work that runs while you're away

Permissions decide what an agent may do while you're watching. Work the Scheduler runs in the background has no one to ask, so Settings has one more row, Tool risk. There you give a tool, or a command such as npm publish, one of six marks: read, write, confirm, irreversible, money, or public.

The last three are the brakes. A background job may not use a tool marked irreversible, money, or public unless its work order names that tool as cleared. A tool marked confirm pauses the job and asks you in Needs you on Home. Approve lets it make that one call and carry on; Deny keeps the job parked. An unmarked tool is allowed. On Home, Tool risk edits the marks for your whole machine; in a project's Claude config, it edits that project's marks, which win. A project can also switch on Also guard interactive sessions in this project to apply the same marks while you're chatting.

The rule of thumb: Settings is for everyone, Agents and Missions are for one job

Claude Code reads every file in this chapter fresh before each Session starts, and none of them know which Session is about to run. A change in Settings or Permissions reaches every current and future Session in its scope, not just the one you have in mind.

So if you want one Session to behave differently, Settings is the wrong lever. Pick a different Agent for it, or give it a Mission that carries the instructions you want. Save Settings and Permissions for what should be true no matter which Session runs.

What you learned

  • The CLAUDE.md row on Home edits ~/.claude/CLAUDE.md for every Session; a project's Claude config edits its own CLAUDE.md and CLAUDE.local.md.
  • Settings has three scopes — User, Project, Local — and Local beats Project beats User. Home edits User; a project's Claude config edits the other two.
  • A project's AGENTS.md is one map for Claude Code, Codex and Gemini; CLAUDE.md is a one-line @AGENTS.md stub. Review MD network ranks what to fix.
  • Permissions, a tab inside Settings, holds Allow, Deny, and Ask rules that stop needless prompts without turning off the safety rail.
  • A Settings or Permissions change reaches every Session in its scope; per-Session behavior belongs on that Session's Agent or Mission instead.
