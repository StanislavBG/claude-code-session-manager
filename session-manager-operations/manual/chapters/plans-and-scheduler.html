Work that runs while you're away — plans and the Scheduler

A big idea doesn't run as one giant task. The architect turns it into small, written work orders, and the Scheduler runs them in the background, in order, while you do something else. This chapter shows you how a work order is written, how the Scheduler decides what to run and when, and how you step in.

A work order is a written contract

When you ask the architect to build something, it doesn't just start typing. It writes a work order first — a short, plain document with four parts, so a dev-lead can pick it up later and know exactly what to do.

PartWhat it holds
GoalOne sentence: what this piece of work is for.
ChecklistHow to know the work is done — checks a dev-lead can run without you in the room.
NotesWhere to look, what already exists, anything the dev-lead shouldn't have to guess.
What not to doThe edges of the job — what's left for a later work order, or left alone.

A dev-lead has no screen to look at and no mouse to click. "Open the app and try it" isn't a checklist item. "Run this test and it passes" is.

Think of it like this: a work order is a ticket you'd hand a contractor who won't be in the room while they build. Everything they need is on the ticket, because you won't be there to answer questions.

From your idea to a queue of work orders

You bring the architect an idea in your own words — a bug to fix, a feature to add. It asks about anything unclear, then splits the idea into small work orders that can each finish on their own. Typing /develop starts this, but saying what you want works just as well.

Each work order joins the Scheduler's queue for your project. A work order can say it depends on an earlier one, and the Scheduler always waits for that one to finish first. Nothing else sets the order. Two work orders with no link between them can run in any order, even at the same time.

Each running work order gets its own copy of your project, so two at once never step on each other's changes. When one finishes cleanly, its result is folded back into your real project.

  1. The architect writes the work order and adds it to the queue.
  2. The Scheduler waits for a free slot and for any dependency to finish.
  3. A dev-lead runs it in its own copy of the project.
  4. It reports back, and its result is folded into your project.

Reading a work order's status

Every work order in the queue carries one status, in plain words:

StatusWhat it means
PendingWaiting its turn — for a free slot, or for a dependency to finish first.
RunningA dev-lead is working on it right now.
CompletedDone, and folded back into your project.
FailedIt ran and didn't finish. The Scheduler will usually try again on its own, and a Retry button lets you send it back sooner.
Needs reviewParked: the run ended, but something didn't check out. The Scheduler is fixing it — nothing is needed from you.
SkippedSet aside, so the work orders behind it can keep moving.

Needs review sounds like a job for you, but it isn't. The run ended, but the final checks didn't agree with its report. Maybe its tests failed, or its changes couldn't be folded in yet.

The Scheduler retries the fold-in, asks the same dev-lead to finish, or sends a fresh agent to find the cause and fix it. These work orders sit under Being fixed. The Needs you count beside it leaves them out and counts only work that wants your eyes, such as a failed work order.

Good to know: if repairs don't work, the Scheduler puts the work order back in the queue up to two more times, half an hour apart, then skips it so the work behind it can run. The Session that wrote it gets one short message saying what happened.

When work waits on a step only you can take

Some work needs a person first — say, signing in to a service. A work order can carry a small check for that step, called a preflight. Before it starts, the Scheduler runs the check. If the check fails, the work order holds.

A held work order stays Pending, with a note that it is waiting on its precondition. Work that depends on it waits too. Your Session gets one message that starts with PRECONDITION HOLD:. It says what is missing, which check failed, which work orders are held, and when the next check runs. It asks you nothing.

The Scheduler checks again after 10, 20, 40, and 60 minutes, then every hour. No agent runs while it waits, so a hold costs nothing. Once you take the step, the next check passes and the work starts by itself. A reset of that work order checks again right away.

Good to know: a held project counts as waiting, not stuck, so no alarms fire. And if a run fails because the step is missing again, the work order goes back on hold instead of into Needs review.

Taking the wheel: pace, pause, and cancel

Every Claude Code job on your machine — Scheduler work and Chat alike — draws from one shared limit, so your laptop never runs more agents than it can handle. You set that limit from the Home tab. Set it to zero and nothing new starts, while running work carries on.

Claude Code also has a usage limit that resets every few hours. Near that limit, the Scheduler pauses itself rather than start work that would fail, and picks back up once the window resets.

  1. Pause stops new work orders from starting. Running work keeps going.
  2. Resume clears any pause, yours or the Scheduler's, and the queue starts again.
  3. Run now starts the next ready work order right away.

To drop a work order that hasn't finished, ask the architect to cancel it. A Pending one is retired; a Running one is stopped. Its row then reads cancelled in grey. A cancel is your choice, so it never counts as a failure and never holds up the Session. A finished work order can't be cancelled — reset it if it should run again.

A stopped run's changes are not folded into your project. They stay on the work order's own side branch. If its change had already landed, that change stays in your project's history.

If other waiting work orders depend on the one you cancel, the cancel is refused and names them. You then choose: cancel them too, point them at a different work order, or drop the link. Cancelled rows leave the queue once their Session is completed and nothing waiting depends on them.

Tasks: one quick run for a script

A Task is one Claude Code run for a project, with no Session, no work order, and no copy of your project. Only a script can start one, and only while Scripts may run Tasks is on for that project. You find that switch in the Scheduler's Tasks view. While it is off, the Scheduler turns every script away.

The switch is your consent, so only you can flip it. You can click it, or ask an agent in your own chat. The agent must quote your words, and a script can never turn it on for itself. A line under the switch says who last changed it and when; for an agent, it shows your quoted words. A Task never creates a Session.

A Task draws from the same shared limit as everything else and goes ahead of waiting work orders. When the limit is two or more and Tasks are on, one slot stays free for your own work. The Tasks view lists each run with its prompt and answer, kept for 30 days by default.

Try this: open the Scheduler tab and watch one work order's status. You'll see it move from Pending to Running to Completed, usually without you touching anything.

What you learned

  • A work order is a written contract: a goal, a checklist, notes, and what not to do.
  • The Scheduler runs work orders in their own copies of your project, waiting only on dependencies, a free slot, or a step only you can take.
  • Needs review is the Scheduler fixing its own work, and a precondition hold resumes by itself once you take the missing step.
  • Pause, Resume, Run now, and cancel let you steer; a cancel is never a failure.
  • A Task is one quick run a script may start only while you allow it.
