# Usage dashboard

A self-contained static page (`index.html` + `dashboard.js`) that renders Session
Manager's anonymous telemetry for the product owner. No build step, no CDN
dependency — `dashboard.js` is a classic `<script src>` (not an ES module) so
the page also works opened as a plain `file://` document, not just served.

This is a **sibling artifact** to the 5-page Project Pages pipeline
(`session-manager-operations/architecture/project-pages-pipeline.md`), not a
6th page generated by it. That pipeline generates marketing/architecture
*content* from a component library and a computed summary; this page is a
live *data view* with its own fetch/render logic and no meaningful "variant"
concept. It happens to live under the same `output/` folder (this project's
`bilko-host` static path is `/projects/session-manager/`, so
`output/dashboard/` maps to `/projects/session-manager/dashboard/`) but is
authored by hand, not by the `project-home-builder` Epic.

## Endpoint contract it consumes

`GET /api/admin/session-manager/usage?days=30`, same origin, gated by
bilko.run's `requireAdmin` (Clerk) — the same gate `/api/admin/observability`
already uses. See the PRD's pinned JSON shape; this page renders exactly
those fields and invents nothing.

**Auth tradeoff, stated plainly:** this HTML file itself is public — it's a
static path on a public site — but it carries no data of its own. Every
number arrives from the gated endpoint, so a signed-out visitor sees an
empty shell with a "sign in at bilko.run/admin" message, not a private page.

## Ranking rule

Issues are ranked by `installsAffected` descending, with `occurrences`
descending as the tie-break only — never the other way around. A single
machine stuck in a crash loop can emit hundreds of correlated occurrences;
ranking by raw count would bury a bug hitting nine separate installs once
each below one user's bad afternoon. See `dashboard.js`'s `rankIssues` and
its test in `tests/unit/usage-dashboard.spec.ts`.

## States

`dashboard.js`'s `init()` renders one of: loading, empty (200 but no
installs/launches/issues in the window — the expected state before any real
telemetry lands), unauthorized (401/403), not-deployed (404 — the expected
state before the bilko.run endpoint PRD ships), network failure, or the full
dashboard. None of these throw or leave a blank screen; each is covered by a
stubbed-fetch test.

## Fixture workflow

Append `?fixture=1` to the URL to render from the committed `fixture.json`
instead of the network — no server, no admin session needed. Use this for
review and for local iteration on layout. `fixture.json` covers all four
sections with multi-version, multi-platform data and includes the
400-occurrences/1-install vs. 12-occurrences/9-installs case to make the
ranking rule visible.

## No PII

The response contract has no install-id, email, username, or hostname
field, and this page never invents one — only aggregate counts
(`installsAffected`, `installs`, etc.) are ever rendered.

## Publishing

Out of scope for this PRD. Publishing this bundle to
`/projects/session-manager/dashboard/` on bilko.run is a separate PRD via
the `bilko-host-publisher` Epic, once a human approves it.
