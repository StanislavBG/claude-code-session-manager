### 1. Stateless

Verdict: PASS

`Skills.tsx` holds `items`, `selectedPath`, `scope`, `view` and `filter` in component state. `items` is rebuilt from disk by `loadItems` on mount, scope change and every `config:changed` event, so it is a projection. `filter`, `view` and `selectedPath` are transient UI. File text lives in the `useConfig` store as `diskRaw` plus a draft, re-read on load and save. `grep -n "localStorage\|sessionStorage" src/renderer/components/tabs/Skills.tsx` returns nothing. The one stateless-adjacent defect (a toggle discarding the unsaved draft) is filed under principle 2 as `skills-F1`.

### 2. Physical files

Verdict: FINDINGS

Reads and writes all hit the real files Claude Code loads: `~/.claude/skills/<name>/SKILL.md` (plus one namespace level), `~/.claude/commands/*.md`, and the `<cwd>/.claude/…` equivalents. Edits go through `useConfig.saveText` → `config.writeText`; the toggle edits only `disable-model-invocation` via `setSkillDisabled`; remove goes through `files.delete`. No sidecar state. The defect is in how the toggle interacts with an open, edited draft (`skills-F1`).

### 3. Current, not hardcoded

Verdict: FINDINGS

The lists come from disk through `listSkillEntries` and `config.listDir`, and `useConfigDirWatch([skills, commands])` re-runs `loadItems`. chokidar's default watch is recursive (`src/main/config.cjs:402`) and emits against the watched root key, so a nested `SKILL.md` edit or add re-lists. `roots()` is the only path source and matches the page invariant; no domain-value array literals exist in the entry. The findings are that listing failures are silent (`skills-F3`) and that commands are only listed one level deep (`skills-F5`).

### 4. One API per feature

Verdict: FINDINGS

Duplicate-API judgments from the planning list:

- `config.listDir` (memory, overview, plugins, skills): **PASS — generic layer.** It is the app's one directory-listing IPC, wrapped by `config.cjs` `validatePath`; no feature owns it. No page adds a parallel method.
- `config.readText` (plugins, skills): **PASS — generic layer.** Same reasoning; `useConfig.loadText` and several libs use it for unrelated files.
- `files.delete` (projects, skills): **PASS — generic layer.** Call sites are `Skills.tsx:188`, `DocumentMenu.tsx:87` and `FileTree.tsx:483`. Each deletes a different thing through the one trash-backed handler.

The real duplication is one level up: *skill discovery* (walk a skills dir, read each `SKILL.md`, parse frontmatter) is implemented three times. That is `skills-F2`.

### 5. Clear separation and platform adherence

Verdict: FINDINGS

Entry imports only `ui/`, `lib/`, `state/` and the shared `Library.tsx`; no other page's owned file is imported. No `process.platform`, no raw z-index, no browser storage, no fs access. Face law holds: `navGroups.ts:72` declares `skills` with `faces: HOME`. `listSkills.ts` is shared with `GlobalControlsSection.tsx` (Dashboard-side), which is the right shape. Platform issues: commands are not read the way Claude Code reads them (`skills-F5`), errors from listing are swallowed (`skills-F3`), and the remove confirmation uses a blocking `window.confirm` (`skills-F6`).

### 6. Lean tests

Verdict: FINDINGS

Two of the page's four test files are `merge`. Together the three Skills test files cover list, description, watch and NavFace scope, but no test covers the toggle or the remove paths (`skills-F7`). `npm run lint:test-smells` was not run; see the candidates table.
